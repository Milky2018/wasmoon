# ISS-114: Require validated modules at the instantiation seam

## Description
The public executor interface accepts `wasm_core/types.Module` directly in `instantiate_module`, `instantiate_module_with_imports`, `instantiate_module_with_init`, and `instantiate_with_linker`. The same `Module` type represents both unvalidated parser output and modules that have passed `wasmoon/validator`, so library callers can bypass validation even though instantiation and JIT code rely on validated invariants.

This is a structural safety problem rather than only a missing call site: validation is an ordering requirement that the interface cannot express.

## Design
Introduce an abstract `ValidatedModule` type produced only by successful core validation, or replace the split parser/validator/executor workflow with a deep module that performs parse, validation, and preparation behind one interface. Make normal instantiation entry points require the validated representation. If an unchecked internal entry point remains necessary for validator or conformance tests, keep it private or name it explicitly as unsafe.

Preserve structured validation diagnostics and avoid coupling the reusable `wasm_core` data model to the Wasmoon runtime.

## Acceptance Criteria
- [ ] Successful validation produces an abstract validated-module representation.
- [ ] Public instantiation entry points no longer accept an arbitrary raw `Module`.
- [ ] CLI, WAST, component-model, preflight, and library call sites cross the validated seam explicitly.
- [ ] Invalid modules cannot reach runtime allocation or JIT compilation through a normal public interface.
- [ ] Validation diagnostics retain function, instruction-offset, and instruction context.
- [ ] `moon check --target native` and the complete MoonBit test suite pass.
- [ ] Core and component WAST runners pass.
