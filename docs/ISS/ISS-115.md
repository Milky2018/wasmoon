# ISS-115: Decouple interpreter runtime state from JIT-native storage

## Description
The `wasmoon/runtime` package imports both `wasmoon_jit` and `wasmoon_jit/jit_ffi`. Interpreter memory uses the C-side `wasmoon_memory_t` descriptor as its mandatory representation, and `Store` embeds JIT-owned `CHeap` and `JITTable` values.

This makes the interpreter runtime inseparable from the native JIT implementation. It also weakens interpreter-versus-JIT differential testing because both paths can share defects in the same C memory and table representation.

## Design
Define runtime-owned memory, table, and GC interfaces at the execution-state seam. Provide separate interpreter and native-JIT adapters where behavior genuinely differs. The interpreter adapter should not require executable-memory, signal, JIT-table, or JIT-GC facilities. JIT state synchronization should happen in an explicit Wasmoon-owned adapter rather than through JIT types embedded in the core `Store` representation.

Do not introduce pass-through interfaces with only one implementation. The target shape needs at least the interpreter adapter and the native JIT adapter, tested through the same runtime semantics.

## Acceptance Criteria
- [ ] `wasmoon/runtime` no longer imports `wasmoon_jit` or `wasmoon_jit/jit_ffi`.
- [ ] Interpreter memory, table, and GC execution can run without constructing JIT-owned values.
- [ ] Native JIT memory/table/GC integration is isolated behind an explicit adapter.
- [ ] Store ownership and synchronization rules are documented at the adapter seam.
- [ ] Interpreter-versus-JIT tests exercise distinct storage adapters while preserving observable Wasm semantics.
- [ ] The interpreter package can be type-checked for every target supported by its non-native dependencies, or any remaining native restriction is documented and enforced narrowly.
- [ ] Native MoonBit tests and core WAST interpreter/JIT suites pass.
