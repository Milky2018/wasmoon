# ISS-633: Keep current capability and architecture documentation consistent

## Description
Current user-facing documentation contains duplicated features, stale platform
scope, and outdated format/path references. README repeats the HTTP 0.3 feature;
`docs/architecture.md` describes artifact v9 while the codec is v11, and marks
Windows native WASI 0.3 as a non-goal despite its existing external CI acceptance.
The component unsupported matrix still references paths from before extraction.

These are examples of a documentation lifecycle problem across current claims,
support matrices, interface contracts, release instructions, and historical
evidence. Fixing three strings would not address the class.

## Scope and Evidence
- Review current README/module READMEs, CLI and embedding guidance, architecture,
  feature/capability APIs, supported-platform matrices, artifact/cache trust and
  compatibility contracts, and corpus acceptance descriptions.
- Distinguish implemented support, configured policy, OS limitation, test evidence,
  experimental status, and unsupported behavior.
- Historical performance and acceptance reports retain their original versions,
  results, and scope; identify superseding evidence without rewriting history.

## Design
Identify authoritative sources and owners for current claims, consolidate
duplicated guidance where practical, and update links to actual public interfaces.
Keep release/behavior changes paired with the affected documentation. Make
trust requirements for executing persisted native code explicit: structural
artifact verification does not establish arbitrary machine-code sandbox safety.

## Acceptance Criteria
- [ ] Record a current-document inventory and reconcile capability/platform/format claims against source, generated interfaces, and exact-version acceptance evidence.
- [ ] Remove duplicate feature claims and stale current versions/paths; current Windows scope and artifact v11 agree with implementation and tests.
- [ ] Current instructions and historical reports are visibly distinguished; local profiles, skips/exclusions, modified external tests, and unmodified upstream results are labeled accurately.
- [ ] Embedding ownership, validation, close/cancel, resource-limit, and persisted-native-code trust contracts state actual guarantees and limitations.
- [ ] Public examples, cross-links, and installation/release instructions are checked in their stated context; main versus published registry evidence remains distinct.
- [ ] Record a lightweight documentation update/review workflow tied to changes in owned APIs and support scope; do not introduce a textual style audit as a substitute for review.
