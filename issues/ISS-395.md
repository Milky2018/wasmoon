# ISS-395: The validator aborts the process on modules it should reject

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: validator, cli, exit-codes, robustness, agent
- Assignee: unassigned
- Created: 2026-08-05
- Updated: 2026-08-10
- External ref: none

## Description
`ValidationContext`'s three type-kind helpers `abort` instead of raising:

```moonbit
fn ValidationContext::get_struct_type(self, idx : Int) -> @types.StructType {
  match self.types[idx].composite {
    Struct(st) => st
    _ => abort("Type at index \{idx} is not a struct type")
  }
}
```

`modules/wasmoon/validator/context.mbt:36-67`. There is no bounds check on
`self.types[idx]` either.

In MoonBit `abort` is a panic, not a raise. It cannot be caught, and on
native it prints its message to **stdout**, `PanicError` plus a backtrace to
stderr, and kills the process with **SIGABRT** — exit 134. So a module the
validator is supposed to reject instead crashes whatever is running it, and
the CLI's exit-code and stream contracts (ISS-376, ISS-387) do not apply
because no CLI code runs.

Measured against a binary built from `b13762bf`:

| Input | Result |
| --- | --- |
| `i64` returned where `i32` declared (control) | exit 1, stdout empty, diagnostic on stderr |
| `struct.get` naming a `func` type | **exit 134 (SIGABRT)**, message on stdout, stderr empty |
| `array.get` naming a `func` type | **exit 134 (SIGABRT)** |
| `struct.get` naming type index 99 of 1 | **exit 134 (SIGABRT), both streams empty** |
| `wasmoon-tools validate` on the same file | **exit 134 (SIGABRT)** |
| any of the above with `--no-jit` | identical — not JIT-specific |

The out-of-range case is the worst: it aborts on the unchecked index before
reaching the message, so the process dies silently with nothing on either
stream.

`wasmoon-tools validate` matters most in principle. Its entire job is to
answer valid or invalid, and it crashes on an invalid module rather than
answering.

Reproduce:

```wat
(module
  (type $f (func))
  (func (export "go") (result i32)
    (struct.get $f 0 (ref.null none))))
```

## Design
The crash frame, from a debug build:

```
abort[StructType]                     abort.mbt:50
  ValidationContext::get_struct_type  context.mbt:54
  validate_instr                      instr_validate.mbt:1621
  validate_expr_with_offset           function_validate.mbt:84
  validate_module_with_context        module_validate.mbt:459
  validate_module_for_execution       path.mbt:40
  run_wasm                            run.mbt:478
```

It aborts inside `validate_instr`, which already raises `ValidationError`.
The channel for reporting this was there and unused.

Two things sit under that, and the second is the root.

**The abort is the validation rule.** Three call sites read

```moonbit
ignore(ctx.get_struct_type(type_idx))
```

The result is discarded. The call exists only so it aborts when `type_idx`
names something else — `struct.new_default` and `array.new_default` read
nothing from the type. So this is not a helper that happens to abort and a
caller that happens to ignore it; the crash *is* how the rule was enforced.
Deleting the abort naively would delete a validation rule with it.

**The signature is total over a partial operation.** `get_struct_type`
returns `StructType`. A type index may name a func or array type, in which
case there is no `StructType` to return, and the signature offers nowhere to
say so. `abort` is what maintains that in the implementation; `ignore(...)`
is what exploits it at the call sites; and the missing bounds check on
`self.types[idx]` is the same shortcut taken once more, which is why the
out-of-range case dies before it can even name the index.

The fix is to make the signature admit the partiality — `raise
ValidationError`, not `Option`, since every caller already raises it and an
`Option` would only move the decision one frame out. Then:

- the implementation reports both failures as errors, bounds first
- the three `ignore(...)` sites keep their call, because it is still the
  rule; what changes is that it now reports instead of killing
- `StructGet` resolves the type before popping against it, and `ArrayNew`
  stops looking the same type up twice

Out of scope here, and assessed separately: `wasm_core/types/types.mbt`
declares the same three accessors `pub`, and `runtime/instance.mbt` has a
third copy. ISS-396 covers them — and the assumption that fixing the
validator would leave them unreachable turned out to be wrong, because the
parser calls them before validation runs.

## Notes
- 2026-08-05: Found while answering what else in the repository resembles
  `native_exit`. The survey counted 83 `abort(...)` calls in library
  packages; the messages are mostly internal invariants ("matched checked
  integer arithmetic above", "use emulation sequence instead") that no input
  should reach. This issue covers the ones that ordinary input does reach.
- 2026-08-05: The same three helpers exist in
  `modules/wasm_core/types/types.mbt:1335-1360` and
  `modules/wasmoon/runtime/instance.mbt:51-85`, each documented as "Panics if
  the type is not a function type". Those are on paths that run after
  validation, so fixing the validator may make them genuinely unreachable —
  worth re-checking once it is fixed rather than assuming either way.
- 2026-08-10: Review found one overlooked invariant abort in the SIMD
  dispatch fallback. Although the main dispatcher currently makes it
  unreachable from parsed input, a focused whitebox test reproduced SIGABRT
  by exercising the internal boundary directly. The fallback now raises
  `UnsupportedInstruction`, and the regression test asserts the exact error.

## Close Notes

The three helpers now bounds-check and raise. Type checking took no ripple
at all: every one of the 34 call sites was already inside a function that
raises `ValidationError`, so the error had been available the whole time and
was being thrown away.

The `ignore(...)` calls stay, with a comment saying why. They are the rule,
not leftovers, and removing them would drop the check that `struct.new_default`
and `array.new_default` name the right kind of type. Two orderings were
corrected in passing: `StructGet` popped its operand before resolving the
type it popped against, and `ArrayNew` looked the same type up twice.

Verified against a rebuilt binary — every row was SIGABRT before:

| Case | Now |
| --- | --- |
| `struct.get` on a func type | exit 1, stdout empty, diagnostic on stderr |
| `array.get` on a func type | exit 1, same |
| type index 99 of 1 | exit 1, same (was: both streams empty) |
| any of the above `--no-jit` | exit 1 |
| `wasmoon-tools validate` | exit 1, "invalid: type at index 0 is not a struct type" |

The tests were run against the unfixed code, per ISS-391's lesson. They do
not merely fail there: the validator test **takes the whole test executable
down with SIGABRT**, which is the defect stated as plainly as it can be —
the abort escapes even the harness meant to contain it.

Two layers, because one of them has to run the real binary: a validator
whitebox test asserting the exact error variants, and three cases in
`scripts/cli_behavior_test.py` asserting status and stream from the built
CLI.

validator 80/80, full native suite 2570/2570, spec corpus 258/258 files and
62563 tests in both modes, no `.mbti` changed.

The 2026-08-10 follow-up removed the remaining validator abort and added a
focused internal-dispatch regression. `UnsupportedInstruction` is now part of
the generated validator interface so callers can distinguish a missing
validator case from a guest type error.
