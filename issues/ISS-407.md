# ISS-407: Fold constant offsets into load and store displacements

## Description

`ScalarLoad` and `ScalarStore` carry a displacement field that is left at
zero while the address is computed into a register beside it. For one
wasm `mem[a] = mem[a] + k` the allocated VCode contains:

```text
i11 Convert(Bitcast(Ptr64, I64))     uses=[v4]  defs=[v11]
i12 IntBinaryImmediate(W64, Add, 0)  uses=[v11] defs=[v12]
i13 IntBinaryImmediate(W64, Add, 4)  uses=[v12] defs=[v13]
i14 Convert(Bitcast(I64, Ptr64))     uses=[v13] defs=[v14]
i15 ScalarLoad(W32, None, I32, 0)    uses=[v14] defs=[v15]
```

Eleven VCode instructions where three suffice. Three separate problems
are visible: an `Add` of zero that is never folded, an address chain
recomputed independently for the load and the store, and a displacement
field sitting unused while a register holds what belongs in it.

## Design

Fold a constant address offset into the memory operand's displacement
when it fits the target's addressing mode, and drop the identity `Add 0`.

This removes the address instructions and, more importantly, the
intermediate values they define, each of which currently competes for a
register. It is adjacent to ISS-405 and touches the same output, so the
two should be measured separately to keep their effects distinguishable.

Non-goal: the `Convert(Bitcast(Ptr64, I64))` pairs, which are pure
type-level no-ops that should never occupy a register at all. Worth its
own issue if measurement shows it matters after this and ISS-405.

## Acceptance Criteria
- [ ] Constant offsets fold into load and store displacements when the
      addressing mode allows.
- [x] Zero pointer offsets are forwarded instead of emitting an add of zero.
- [ ] The measured effect is reported separately from ISS-405.
- [ ] Workspace tests and the WAST corpus pass in both modes.
