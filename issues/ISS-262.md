# ISS-262: Place cold live ranges outside hot loops

## Metadata
- Type: bug
- Status: open

## Description

The production allocator chooses the wrong values to spill in the
`pwhash_scrypt_ll` Salsa20/8 kernel. `func_42` has sixteen loop-carried state
words and several address indices that are used before and after the arithmetic
loop. Wasmoon keeps many of the cold indices in physical registers and assigns
hot state values to stack slots. The static arithmetic loop therefore contains
19 reloads and 8 spills; Wasmtime spills dormant indices outside the loop and
keeps all Salsa state in registers, producing no stack access in the arithmetic
body.

The problem is a placement and splitting defect, not insufficient loop
weighting in the abstract. The allocator must distinguish a value that is live
through a hot region but unused inside it from values used on every iteration.

## Design

Extend the target-neutral regalloc planning/allocation path so a cold
live-through segment can be split and parked outside a hot loop region. Prefer
evicting dormant address/index ranges over frequently used loop-carried state.
Use CFG and use-position information already owned by `regalloc`; do not encode
Salsa operations or AArch64 registers in the policy.

The target is not “never spill.” Address indices may live in stack slots between
the load and writeback phases. The requirement is that the repeated arithmetic
region retains its hot state in registers.

## Acceptance Criteria

- [ ] A focused regalloc test models cold values spanning a loop and hot values
      used on every iteration, and locks the intended split/spill decision.
- [ ] `func_42` has no allocator-generated spill or reload inside the
      `add`/`ror`/`eor` arithmetic loop.
- [ ] Cold address/index values may be saved before the loop and reloaded after
      it without extending hot live ranges.
- [ ] The change remains target-neutral and reserves no physical register.
- [ ] Regalloc, AArch64 target, native, and WAST correctness suites pass.
