## Description
MilkIR currently stores complete instructions directly in block layout while
the verifier and several optimization passes independently reconstruct dense
`Value`-to-definition tables. This repeats work, couples SSA definition
identity to instruction placement, and prevents the optimizer from expressing
unplaced alternative instructions directly in the canonical IR.

Replace that ownership model with an authoritative data-flow graph and a
separate instruction layout. Build the bounded aegraph optimizer on that DFG
so GVN, alternative construction, cost extraction, LICM, rematerialization,
and final placement share one value graph instead of rebuilding partial
definition models in each pass.

## Design
The next pre-1.0 minor release may make a clean source-level break to the
MilkIR interface. Do not retain the current `Block.instructions : Array[Inst]`
ownership model beside the new representation merely for compatibility.

`Function` will own a DFG containing stable `Value` and `Inst` identities and
a separate layout containing ordered `InstId` references. `ValueDef` is the
authoritative definition relation and supports function parameters, block
parameters, instruction results, and an optimizer-private `Union` state.
Instruction and value IDs remain stable for the lifetime of a function;
deletion leaves tombstones until an explicit compaction phase. Persistent use
lists are out of scope: use counts and use lists remain derived optimizer state.

The optimizer may temporarily admit typed `Union` definitions and unplaced
pure instructions, but these states are private to `OptimizerSession`. Normal
verification and every optimizer exit require a fully elaborated function.
The session stages placement and commits layout only after successful
extraction; an optimizer failure must leave the input function verifiable.

Only pure, non-trapping, single-result instructions participate in aegraph
alternatives initially. Multi-result, effectful, trapping, call, memory-write,
and control-flow instructions remain in the side-effecting skeleton. A single
central `InstEffects` classification defines memory, trapping, call, and other
observable effects. Rewrites preserve exact WebAssembly and MilkIR semantics;
fast-math and trap-timing relaxation are out of scope.

MilkIR optimization remains target-neutral. Machine addressing, immediate
folding, and instruction fusion stay in direct x64 and AArch64 lowering. O2
uses bounded deterministic candidate and recursion limits with work
proportional to reachable pure IR. O3 uses a larger bounded budget but never
unbounded saturation. Budget exhaustion may stop producing alternatives but
must not disable canonicalization, GVN, memory correctness, or verification.

The intended high-level order is:

```text
normalize
-> loop canonicalization / unrolling / induction transforms
-> one bounded aegraph + GVN + scoped elaboration
-> CFG cleanup
```

Do not run a complete O2 pipeline both before and after loop transforms.

All rewrite rules are handwritten MoonBit. Dispatch is direct and organized by
root opcode, with shared typed helpers for definition lookup, constants,
commutative operands, legality, and candidate construction. Do not add a rule
schema, generator, second opcode language, generic runtime matcher, rule-bucket
scan, or copied e-graph nodes. Mechanical duplication is preferable to owning
and compiling a second rule language; factor helpers only when they preserve a
local, readable execution path and serve multiple concrete rules.

## Acceptance Criteria
- [x] MilkIR has one authoritative DFG for value definitions and instruction data, separate from block layout.
- [x] Blocks order stable `InstId` references rather than owning duplicate complete instructions.
- [x] Builders and mutation methods maintain `ValueDef`; the verifier validates it instead of reconstructing it as the primary definition source.
- [x] Instruction and value IDs remain stable across ordinary transformations, with deletion represented safely until explicit compaction.
- [ ] Optimizer-private typed `Union` values and unplaced pure instructions cannot escape a successful or failed optimization session.
- [ ] Use lists, dominance, GVN scopes, alias state, memory versions, costs, and selections remain derived session state rather than permanent `Function` state.
- [ ] A central effect model prevents rewrites and placement from changing observable traps, memory behavior, calls, or exact floating-point semantics.
- [ ] The initial aegraph covers pure single-result instructions while multi-result and effectful instructions remain in the skeleton.
- [ ] MilkIR cost and rewrite legality remain target-neutral; target-specific selection stays in x64 and AArch64 lowering.
- [ ] O2 and O3 have deterministic bounded work without instruction-count cliffs or unbounded saturation.
- [ ] O3 performs structural loop transforms before one full aegraph/elaboration pipeline rather than invoking O2 twice.
- [ ] Every rewrite rule is handwritten MoonBit behind direct per-opcode dispatch, with no schema, generator, generic runtime matcher, or bucket scan.
- [x] Public documentation describes the source-breaking MilkIR interface migration for the next minor release.
- [ ] Focused optimizer, verifier, JIT/interpreter differential, AEGIS, and representative corpus gates show preserved correctness and no material compile-time regression.

## Notes
- 2026-09-03: Architecture decisions were consolidated after ISS-458 removed the duplicate production e-graph IR.
- 2026-09-03: The deleted Wasmoon matcher described 276 rules and 360 guards in 690 schema lines, used a 488-line Python generator, and emitted 3,951 lines; all old rule files together were 12,897 lines. At the pinned local Wasmtime revision, Cranelift expresses 708 optimization rules in 2,353 ISLE lines plus a 569-line optimization prelude and generates a 19,269-line Rust matcher. The reusable ISLE compiler itself is approximately 8,863 Rust lines. These measurements establish that generation can reduce per-rule source size and produce direct trie dispatch, but only by accepting a substantial compiler/tooling Module and much larger generated compilation input.
- 2026-09-03: Rewrite-rule authoring was resolved in favor of handwritten MoonBit. The project accepts the additional per-rule source in exchange for direct debugging, no generator maintenance, no generated-source compilation cost, and no second rule-language seam.
- 2026-09-03: Implementation started with the authoritative DFG/Layout ownership model. Union values and broad rule migration remain later stages after the core representation and verifier are stable.
- 2026-09-03: The first implementation stage added construction-time `ValueDef` binding and a stable function instruction arena. Verification now checks the stored DFG definition against final placement instead of rebuilding definitions. Builder constant lookup, DCE, direct acyclic rewriting, and rematerialization now use authoritative O(1) definition lookup. CFG block-parameter retention updates DFG definitions through one mutation method; this fixed nine strict native failures exposed by the initial implementation.
- 2026-09-03: Stage-one validation passed 199 MilkIR tests, all 2,202 native tests with `VCODE_REGALLOC_VALIDATION=1`, warning-73 checking, generated-interface refresh, and the module-boundary audit. Three measured AEGIS-128L runs produced a 67,266 us compile median and stable 67,792-byte code, versus the recent ISS-458 record of 69,780 us and 67,792 bytes. Capture: `/tmp/wasmoon-iss459-aegis.NI8PcS`.
- 2026-09-03: Block layout writes are now localized behind `Block` mutation methods. LICM, strength reduction, CFG merging, DCE, GVN, and rematerialization no longer mutate the instruction array directly. This is the preparatory seam for replacing layout-held instruction references with stable IDs. Strict native validation remained 2,202/2,202 after the change.
- 2026-09-03: The second implementation stage replaced `Block.instructions : Array[Inst]` with a private `Array[InstId]` layout backed by the function instruction arena. Public consumers now use count/index queries or a zero-copy ID view plus arena lookup. Native selection and lowering traverse the ID view without materializing instruction arrays. A white-box regression verifies that DCE removes an ID from layout while both the deleted arena entry and surviving instruction ID remain stable. The MilkIR module documentation records the source-breaking pre-0.15 API migration.
- 2026-09-03: Stage-two validation passed 200 MilkIR tests, all 2,203 native tests with `VCODE_REGALLOC_VALIDATION=1`, warning-73 checking, generated-interface refresh, install, and the module-boundary audit. The AEGIS-128L focused gate remained code-size identical at 67,792 bytes and measured a 67,426 us compile median, +0.24% versus the 67,266 us stage-one baseline (within noise); elapsed median improved from 872 ms to 842 ms. Capture: `/tmp/wasmoon-iss459-layout-aegis.ZJvmHL`.
- 2026-09-03: A first attempt to distinguish unplaced instructions from deletions stored `Unplaced` / `Placed(block)` / `Deleted` for every arena entry and updated it on every placement. Although semantically direct, the extra per-instruction array push and placement write regressed the AEGIS compile median to 75,274 us (+11.90%). That implementation was removed rather than accepted.
- 2026-09-03: The retained deletion model allocates a lazy dense tombstone bitset only when an instruction is actually deleted. Moves do not create tombstones, and verification rejects both unplaced non-tombstone instructions and tombstones that remain in layout. The final focused AEGIS gate measured a 64,274 us compile median (-4.45% from stage one), 785 ms elapsed median, and unchanged 67,792-byte code. Capture: `/tmp/wasmoon-iss459-layout-tombstone-aegis.EQ9A0L`.
