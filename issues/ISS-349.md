# ISS-349: Preserve guest progress in component blocking waits

## Metadata
- Type: bug
- Status: closed

- Assignee: codex
- Created: 2026-07-30
- Updated: 2026-07-30
- External ref: none

## Description
`ComponentInvocation::poll` collapses both a cooperative guest `Yield` and a
genuinely blocked guest task into `InvocationPending`. `wait` then asks only
side tasks and the host reactor for progress. With no side task or reactor, it
reports deadlock even though the saved guest continuation can resume on the
next scheduler step.

## Design
Keep the stable public poll contract at `Pending | Ready`, but preserve
`Progressed | Blocked | Ready` inside the invocation driver. Blocking waits
must immediately continue after guest progress and consult the host reactor
only after the guest and nonblocking side-task scheduler cannot advance.

## Acceptance Criteria
- [x] A stable facade black-box component that directly calls `thread.yield`
  completes through `ComponentCall::wait`.
- [x] Public `ComponentCall::poll` remains nonblocking and retains its current
  `Pending | Ready` contract.
- [x] Blocking wait reports deadlock only after the internal driver reports a
  genuine blocked state with no host readiness source.
- [x] Focused facade tests and the full native test suite pass.

## Close Notes

`ComponentInvocation` now has a private drive result that preserves ready,
progressed, and blocked states. Public polling still maps both nonterminal
states to `InvocationPending`; blocking wait immediately drives a progressed
guest continuation and consults the blocking host reactor only after a genuine
blocked result.

The stable facade black-box suite covers interpreter wait, interpreter
`Pending -> Ready` polling, and native JIT wait for a component that directly
calls `thread.yield`. Verification passed with 2495/2495 native tests and the
official Component Model 0.3 async suite at 24/24 files and 153/153 commands in
both JIT and interpreter modes.
