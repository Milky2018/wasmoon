## Question

What structured verification must run after MilkIR-to-MachV lowering, after MachV target lowering, after register allocation, and before emission so malformed or cross-target IR cannot reach a backend abort or silent miscompile?

## Acceptance Criteria

- [ ] Every pipeline seam has a named input state and verification responsibility.
- [ ] Target legality, SSA/CFG validity, operand contracts, allocation constraints, and allocated-form invariants have single owners.
- [ ] Verification failures remain structured errors through Wasmoon JIT integration.

## Notes
- 2026-07-15: Verification must not depend on construction history or mutable validator closures stored in IR data.
- 2026-07-16: Claimed for a HITL Wayfinder decision session using grilling, domain modeling, and deep-module verification seam analysis. No production implementation will occur while resolving this ticket.
- 2026-07-16: Decided that every public pipeline stage validates its ordinary mutable input and validates its output before success. Callers do not orchestrate checks, and safe interfaces expose no verification-disable option. Each representation owns its verifier as the single fact source; private helpers may rely only on invariants established within the same stage call. Verification has no wrapper, closure, history, version stamp, or permanent state and must remain deterministic linear or near-linear work.
- 2026-07-16: Decided that the MachV checkpoint validates only complete target-neutral structure and semantics: function ownership and canonical identities, signatures and value types, rooted reachable CFG with typed edge arguments, strict SSA dominance, terminator and return/tail-call contracts, every opcode/immediate contract, and internally consistent effect, trap, unwind, GC, and cancellation summaries. It neither checks target availability nor reads physical registers, ABI layouts, stack or frame facts, source-dialect validators, or construction history. Failure is a read-only structured `MachVVerifyError` with a precise function/block/instruction site.
- 2026-07-16: Decided that Target VCode remains strict SSA through register-allocation input. It retains function-owned virtual values, block parameters, and typed edge arguments. Target lowering may split edges and insert copies only with fresh definitions; fixed/tied constraints and two-address forms remain allocation facts. Regalloc alone performs SSA destruction by returning edge parallel-move edits, while Target VCode remains unchanged. This preserves dominance verification and target-level optimization without path-sensitive reaching-definition analysis.
- 2026-07-16: Decided that each target exposes one static Target VCode checkpoint. Internally, a shared generic verifier checks ownership, dense storage, CFG/SSA, instruction placement, operand/clobber/metadata ranges, constraint structure, stack objects, and safepoint references. A target-owned exhaustive verifier checks every instruction's typed operand contract, body or terminator role, immediates, lanes, addressing modes, enabled features, physical constraints, ABI roles, call layouts, and emitter coverage. There is no validator callback or dynamic target verifier; structured errors distinguish shared structure from target legality while retaining precise sites.
- 2026-07-16: Decided that Allocation binds structurally to one Target VCode function rather than to a version stamp. It carries the source owner identity, and entries reference stable instruction handles, operand indices, expected vreg handles, and stable edge/program-point handles. Handles are never rebound after deletion. Allocation verification performs a linear bijection against current operands and edits, rejects missing, duplicate, stale, replaced, deleted, or cross-function entities, and then rechecks liveness legality. Mutations that preserve the exact allocation contract may remain compatible; there is no generation, hash, frozen wrapper, or prior-verification state.
- 2026-07-16: Decided that a target-owned Allocation checkpoint first revalidates Target VCode, then composes the generic regalloc checker with target machine-environment checks. Generic checks cover structural binding, register/spill classes, fixed/tied/timing constraints, interference, call clobbers, edge moves, edit locations, spill slots, and live GC roots at safepoints. Target checks cover ISA register banks, reserved registers, persistent roles, materializable scratch strategies, and the callee-saved set passed to frame planning. All failures are structured `AllocationVerifyError` values; checker aborts are forbidden.
- 2026-07-16: Decided that Frame Layout verification covers the complete Target VCode, Allocation, and FrameLayout triple. It validates common ownership and stable stack-object identities; unique aligned non-overlapping ranges for spills, callee saves, explicit objects, and outgoing areas; frame and call-site ABI alignment; shadow, argument, and return regions; incoming bases; paired persistent/callee-save preservation; tail-call teardown; GC and unwind offsets; and target encoding or expansion support for every frame operation. Frame planning checks before success, and public emission rechecks before writing bytes. Failure is a structured `FrameVerifyError`.
- 2026-07-16: Decided that each target emitter first verifies the Target VCode, Allocation, and FrameLayout input, then encodes into private buffers with structured `EmitError` failures and no reachable abort. After branch relaxation, constant-pool placement, label resolution, relocation construction, and metadata offset assignment, a Code Object checkpoint validates all labels and branch targets, relocation kinds and bounds, section and pool ranges, instruction-boundary metadata, and the declared architecture and feature contract. Only a complete verified unlinked code object may escape; partial bytes never do. Production does not require a disassembly round trip, though CI may add one. Wasmoon linking and executable-memory installation remain downstream.
