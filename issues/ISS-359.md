# ISS-359: Defer component runtime close across native execution callbacks

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: component-model, native-jit, continuation, lifecycle, reentrancy, tests, agent
- Assignee: codex
- Created: 2026-07-30
- Updated: 2026-07-30
- External ref: none

## Description
The public native `on_execution` observer runs before a suspended native
outcome has been installed in the scheduler-owned `ComponentInvocation`.
If the observer closes the runtime, cancellation sees no continuation and
linker teardown closes the JIT context and code mapping. Control then returns
to the native adapter, which wraps and publishes the now-unowned continuation.
This can leak the continuation or access released native state.

## Design
Treat public component execution as a reentrant lifecycle boundary. While an
invocation is actively driving, cancellation records a request instead of
cleaning the task immediately. Once the native outcome has been installed, the
driver performs the pending cancellation. Runtime close marks the facade
closed immediately but defers linker, host, and JIT teardown until the active
public execution boundary exits.

Do not expose native continuation state or add a test-only release counter.

## Acceptance Criteria
- [x] Closing a runtime from a resumable `on_execution` callback reports
      structured `Cancelled` without publishing a pending dangling call.
- [x] The returned native continuation is cancelled exactly once before the JIT
      context and code mapping are closed.
- [x] Runtime close remains terminal and idempotent during reentrant execution.
- [x] Poll, wait, join, normal completion, and ordinary cancellation regressions
      remain green.
- [x] A public black-box native facade test covers callback-driven close.
- [x] The ownership guard spans every core execution and suspended
      continuation, including scheduler-driven subtasks and guest threads.
- [x] Linker teardown cannot overtake either an in-flight outcome or an already
      published continuation.

## Notes
- 2026-07-30: Initial issue.
- 2026-07-30: A public black-box regression reproduced the old behavior as a
  pending call after the callback closed its runtime.
- 2026-07-30: Reopened after review found that the root invocation guard does
  not itself cover an in-flight scheduler subtask whose continuation has not
  yet been returned to and published by the scheduler.
- 2026-07-30: Reproduced the missing low-level invariant: reentrant linker close
  produced `("published", ["engine"])`, proving that engine teardown happened
  before the in-flight continuation became scheduler-owned.
- 2026-07-30: Added a linker-scoped core execution lease that transfers into
  every suspended continuation and survives repeated resume/suspend cycles.

## Close Notes

Closed again on 2026-07-30 after adding scheduler-wide ownership coverage.

- Active invocation cancellation now records a request while the native
  execution step is driving, then consumes the returned continuation before
  reporting `Cancelled`.
- Runtime close is terminal immediately but defers host, linker, JIT-context,
  and code-mapping teardown until the public execution boundary exits.
- The callback-close regression now observes
  `([Resumable], Cancelled, RuntimeClosed)` and exercises idempotent close.
- Core execution now holds a linker lease from initial invoke through every
  suspended continuation. Closing marks the linker terminal, cancels published
  continuations, converts a late-returned outcome to `Cancelled`, and performs
  engine/Store teardown only after the final lease is released.
- Added exact ordering regressions for close during an in-flight outcome and
  close after continuation publication. Existing public root and side-task
  callback-close regressions remain green.
- Validation passed: `moon check --target native --warn-list @73`;
  native tests 2507/2507; runtime implementation tests 34/34; stable Component
  Model 0.2 matrix 23/23 files and 845 commands; async 0.3 matrix 24/24 files
  and 153 commands; Python gates 65/65; component security and module-boundary
  audits.
