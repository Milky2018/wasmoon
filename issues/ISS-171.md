# ISS-171: Validate contextual Wasm dialect contracts against module types

## Metadata

- Assignee: unassigned
- Created: 2026-07-14
- Updated: 2026-07-14
- External ref: none

## Description
Wasm dialect validation can derive fixed operand and result contracts directly from an extension instruction, but operations such as `call(func_idx)`, `call_indirect(type_idx)`, `struct_get(type_idx, field_idx)`, `array_get(type_idx)`, and `throw(tag_idx)` depend on module function, type, field, element, or tag metadata. The current `wasm_isa_lower.lower_function` interface does not receive that metadata, so it cannot independently prove that producer-supplied contextual types match the referenced module entities.

## Design
Define a minimal Wasm validation context owned by the Wasm adapter and pass it at the production lowering seam. Resolve function signatures, indexed function types, struct field types, array element types, and tag signatures through that context. Keep MilkIR independent of `wasm_core`; the generic extension validator should continue to expose only a read-only instruction view. Standalone lowering without module metadata must either reject contextual operations or require explicit resolved contracts instead of silently trusting instruction-local declarations.

## Acceptance Criteria
- [ ] Direct, indirect, and reference calls are checked against resolved function signatures.
- [ ] Struct and array operations are checked against resolved aggregate types.
- [ ] Throw operations are checked against resolved tag signatures.
- [ ] Invalid indices and contextual type mismatches return structured validation errors before instruction selection.
- [ ] MilkIR core does not import Wasm-owned packages or hard-code Wasm opcodes.
- [ ] Production JIT paths pass trusted module validation context and targeted forged-IR regressions pass.
