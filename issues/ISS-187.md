## Question

Which call, return, tail-call, stack-argument, multi-value-result, clobber, context, and frame facts remain semantic in MachV, and which are introduced only when target lowering applies the selected native ABI?

## Acceptance Criteria

- [ ] MachV call semantics are specified without physical registers or host calling conventions.
- [ ] Target VCode ownership of fixed registers, clobbers, outgoing areas, prologues, epilogues, and special registers is explicit.
- [ ] Wasmoon embedding context and runtime-symbol responsibilities remain outside reusable compiler infrastructure.

## Notes
- 2026-07-15: This decision must cover both internal Wasm calls and foreign/helper calls.
- 2026-07-15: Claimed for a HITL Wayfinder decision session using grilling, domain modeling, and deep-module seam analysis. No production implementation will occur while resolving this ticket.
- 2026-07-15: Decided that MachV preserves a complete logical call contract: ordered typed parameters and results, explicit call arguments and SSA results, and an explicit ordinary `Ptr64` execution-environment value when the callee semantically requires one. MachV does not name or describe VMContext. Hidden return-area pointers, register placement, stack offsets, outgoing areas, and sret registers are ABI implementation details introduced only by target lowering.
- 2026-07-15: Decided that each MachV function entry and Semantic Call explicitly selects a small target-neutral `CallProtocol`: `Internal` for the embedding/compiler-defined convention or `Platform` for the host platform C ABI. Protocol is independent of direct, indirect, or external callee identity and contains no placement facts. Target lowering maps the two variants to statically prepared target ABI plans without opaque ids, registries, or runtime lookup.
- 2026-07-15: Decided that machine-target modules own ABI planning, platform convention rules, validation, and target-specific convention types. Wasmoon JIT owns only its internal cross-language ABI contract, including execution-environment and reserved runtime register roles, and asks the selected target to validate and materialize that contract. A target lowering context holds prevalidated internal and platform conventions selected directly by `CallProtocol`; MachV and MilkIR-MachV lowering contain neither physical layouts nor Wasmoon context vocabulary.
- 2026-07-15: Decided that a target ABI convention is a deep module that derives an immutable per-entry or per-call `CallLayout` from a logical signature. The layout owns exact parameter/result locations, hidden return-area parameters, overflow stack offsets and alignment, fixed constraints, and clobbers. Target lowering alone consumes it and immediately materializes Target VCode operations, allocation facts, and outgoing-area requirements. Layout caching is a private target optimization, not a MachV registry or caller responsibility.
- 2026-07-15: Decided that MachV multi-results remain ordered logical SSA results. A `CallLayout` assigns each result to a register or caller-owned return-area slot. Target lowering creates an aligned abstract outgoing return-area stack object, passes its address through the convention's hidden location, makes the callee store overflow results there, and reloads them into caller virtual results after return. Physical SP/FP offsets wait for frame layout; a function may reserve and reuse the maximum outgoing call area. `GcRef64` result slots retain type and liveness facts for stack-map construction.
- 2026-07-15: Decided that stack arguments remain logical MachV values. Target lowering maps callee parameters to register moves or symbolic `IncomingArgSlot` loads and caller arguments to stores in a caller-owned `OutgoingCallArea`. The outgoing area covers platform shadow space, stack arguments, and return areas and is reserved to the function's maximum call-site requirement. Incoming slots are views into the caller frame, not callee-owned stack objects. Target frame layout resolves SP/FP offsets, return-address adjustments, and alignment; MachV has no stack-adjust, outgoing-store, or stack-base ABI pseudo-operations.
- 2026-07-15: Decided that target lowering records call allocation facts only once in Target VCode side tables. Register arguments, results, indirect callees, and hidden ABI values use explicit fixed or tied operands with correct before/after-call timing; caller-saved registers are call clobbers, while used callee-saved registers drive later frame saves. Target call instructions retain only encoding-relevant call form and immediates, not duplicated argument counts, result classes, or clobber classes. Regalloc satisfies fixed constraints and inserts moves.
- 2026-07-15: Decided that MachV execution-environment and runtime values remain ordinary typed SSA values. Internal ABI target lowering may map a frequently used long-lived role to a precolored Target VCode vreg selected by the Wasmoon Internal ABI Contract. The target validates that persistent roles use legal callee-saved registers; used roles leave the allocatable pool and drive frame save/restore. Optional context caches and extra-results roles reserve registers only when materialized. Entry lowering moves from argument locations into precolored values; MachV contains no physical or pinned-context concept.
- 2026-07-15: Decided that each target performs post-regalloc frame planning from Target VCode, Allocation, and the entry convention. The resulting `FrameLayout` owns physical offsets for spills and stack objects, callee-save locations, the outgoing area, alignment, total size, frame-pointer choice, incoming-argument bases, and unwind frame facts. The target emitter consumes VCode, Allocation, and FrameLayout to generate prologues, epilogues, and stack addressing. MachV and Target VCode contain no prologue/epilogue operations or final SP/FP offsets.
- 2026-07-16: Decided that a MachV tail call is a no-result terminator with callee, logical signature, explicit arguments, and protocol; its result types must exactly match the enclosing function. The architecture guarantees true tail calls only for `Internal` to `Internal`. Target lowering must prove layout compatibility, forward the incoming hidden return-area pointer unchanged, arrange arguments, and represent frame teardown plus the final jump for target emission. Unsupported layouts return a structured error and never degrade to a normal call followed by return.
