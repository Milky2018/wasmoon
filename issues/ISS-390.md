## Description
ISS-368 removed the sanitizer gate because it worked by compiler
interception: `MOON_CC` pointed at a shim that appended `-fsanitize` to
every command moon issued.

That removal was right, but the reason recorded alongside it was not. Both
that commit and ISS-323 claim moon supports no other route. ISS-323's actual
finding is narrower and still correct — the `CFLAGS`, `CXXFLAGS` and
`LDFLAGS` **environment variables** are ignored — but moon has first-class
config fields for the same purpose:

```json
{ "link": { "native": {
    "cc": "gcc", "cc-flags": "-O2 -DMOONBIT", "cc-link-flags": "-s" } } }
```

Measured on a two-package probe module, with the flags declared on one
package:

| Command | Flags applied |
| --- | --- |
| that package's executable link | yes |
| that package's `internal_test.exe` and `blackbox_test.exe` | yes |
| test binaries of a *different* package that imports it | no |
| `native-stub` C compiles (`helper.c` -> `helper.o` -> `.a`) | no |
| moon's own runtime objects | no |

The scope looks narrow but is not, because MoonBit's native pipeline is
whole-program: `moonc link-core` merges every package's `.core` into a
single generated `.c`, and that one file is what the flagged command
compiles. The probe's `app.c` contained the dependency package's MoonBit
function, and its `liblib.a` held only the hand-written stub. So
`cc-flags` on one package instruments **all MoonBit code in the binary**,
not just that package's.

## Design
Add one package whose `moon.pkg` carries
`-fsanitize=address,undefined -fno-omit-frame-pointer` in `cc-flags` and
`cc-link-flags`, holding blackbox tests that drive the runtime and JIT.
CI runs that package's tests; nothing else changes, and no environment
variable or wrapper is involved.

This also answers the cost problem ISS-368 failed to solve. That gate's 46
to 57 minutes was the union of six distinct dependency closures, each
compiled separately. One package is one closure — by the old attribution,
the largest single closure was 12 to 15 minutes.

Two limits to record rather than discover later:

- **Hand-written native stubs cannot be instrumented this way.** `cc-flags`
  lands on the link command; stubs are compiled separately into per-package
  archives, and the probe confirmed they do not receive the flags. That
  leaves `jit_ffi/fiber.c`, the JIT stubs, and the logger/async/wasi stubs
  outside the coverage — hand-written C being exactly where memory bugs are
  most likely. This is a real loss against the shim, which instrumented
  them.
- **Whitebox tests cannot move into the package.** Five of the old gate's
  nine files are `_wbtest.mbt` and must stay in the package they test.
  Declaring the flags in those five packages instead would sanitize every
  local `moon test` of them, and moon documents no way to make the config
  conditional.

So this is not an equivalent replacement for the shim. It covers less, by a
mechanism that is declarative, version-controlled, and confined to one
package.

## Acceptance Criteria
- [ ] A dedicated package builds with ASan and UBSan through
      `link.native`, with no `MOON_CC` and no sanitizer environment
      variables in the workflow.
- [ ] Instrumentation is verified from the built binary, not assumed.
- [ ] A deliberately introduced memory error in MoonBit code is caught by
      the gate, proving coverage rather than inferring it from flags.
- [ ] What the gate does not cover — native stubs, moon's runtime,
      whitebox tests — is stated where a reader of the workflow will see it.
