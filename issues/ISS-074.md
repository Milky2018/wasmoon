# ISS-074: Replace wasm frontend translation parameter list with typed context

## Description
ISS-073 narrowed `modules/wasmoon/wasm_frontend/ir` so it no longer exposes
`Translator`, `FuncEnvironment`, or MilkIR re-exports. However, the remaining
public decoded-body entry point still exposes the translator's internal metadata
needs as a long parameter list:

- function type arrays and function type indices
- import counts and import type indices
- memory/table/global/type/tag metadata
- cross-module remap fields
- memory min/max and memory64/page-size metadata
- embedding runtime layout

That is still an API debt. Callers should not need to know which exact decoded
module arrays the translator happens to consume internally. The frontend should
own a typed, immutable translation context and expose a smaller entry point over
that context.

## Design
Introduce a Wasm frontend IR translation context that packages the decoded
module metadata required by `translate_function_body`. Keep the existing
translation behavior and internal `Translator` implementation unchanged; this
issue is about API shape and ownership, not semantics.

Expected shape:
- A public context type such as `TranslationContext`.
- A context constructor that derives metadata from a decoded module where
  possible, while still accepting the embedding environment and any Wasmoon-owned
  runtime overrides explicitly.
- A public body translation function that takes the context plus the minimal
  per-function inputs.
- The production CLI compile path should build/reuse the context and stop
  passing the translator's full internal metadata list at every function.

Constraints:
- Do not rewrite translation logic.
- Do not change MilkIR, lowering, register allocation, emission, or JIT
  correctness behavior.
- Do not move Wasmoon runtime address resolution or native JIT ownership into
  `wasm_frontend/ir`.
- Keep the context immutable from the public caller's point of view.

## Acceptance Criteria
