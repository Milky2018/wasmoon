## Question

Given the standing decision that MachV retains single-definition virtual registers and block parameters, what exact CFG, dominance, edge-argument, instruction-order, effect-order, terminator, and mutation invariants must MachV expose and verify?

## Notes
- 2026-07-15: MachV retains single-definition values and block parameters; this ticket resolves the detailed contract rather than reopening that direction.
- 2026-07-15: Claimed for a HITL Wayfinder design session using grilling, domain modeling, and deep-module interface analysis.
- 2026-07-15: Every successor-bearing terminator uses one uniform `Edge(target, arguments)` contract. Each edge carries its own ordered SSA arguments, whose count and types exactly match the target block parameters. Jump, conditional branch, and multi-way branch do not use bare target ids or synthetic jump-only blocks to compensate for missing edge arguments.
- 2026-07-15: A verified MachV function has a nonempty rooted CFG. Its first block is the unique entry, has no incoming edges or block parameters, and receives function parameters as the initial SSA values. Every other block is reachable from entry. Builders and transforms may temporarily create unreachable blocks, but must remove or reconnect them before verification. CFG order does not select fallthrough or final machine layout; those decisions belong downstream.
- 2026-07-15: A MachV block is an opaque dense handle carrying a private function owner identity. The function owns the canonical block data, order, and entry; edges carry block handles rather than integer ids. Block creation, lookup, and mutation reject foreign handles before changing state. Clone, rebuild, and deserialization create a fresh owner and remap blocks and edges. Dense ids are internal indices and printed or serialized identities, not cross-function identity.
- 2026-07-15: A MachV instruction is an opaque function-owned handle into canonical instruction data containing its semantic operation, operands, results, and metadata. It appears exactly once in one block's ordered instruction list. Function mutation owns create, move, replace, and remove; a removed handle is never rebound within that function. Results remain independent MachV values. Clone, rebuild, and deserialization remap instructions under the fresh function owner.
- 2026-07-15: Every MachV value has exactly one definition as a function parameter, block parameter, or instruction result. Function parameters are initial values; block parameters are defined simultaneously at block entry; instruction results are defined after their instruction. Every instruction, edge, and terminator use must be dominated by its definition, with same-block definitions strictly preceding uses. Edge arguments are parallel uses at the source terminator and exactly match target parameters. MachV has no phi instruction. Critical edges remain legal; Target VCode lowering may split them and insert parallel copies or leave strict SSA for target constraints.
- 2026-07-15: A block's ordered instructions followed by its terminator define baseline program order. Each operation has canonical memory, call, trap, unwind, and safepoint summaries rather than caller-selected flags. Pure non-trapping instructions may move when SSA remains valid; potentially observable instructions may move only with proof that effects, aliasing, trap order, unwind, safepoints, and external behavior remain equivalent. Terminators are last. Metadata moves with stable instruction identity. MachV has no effect-token values; Target VCode preserves observable order while scheduling unconstrained work.
- 2026-07-15: Every block has exactly one terminator from `Jump(Edge)`, `Branch(I32, Edge, Edge)`, `Switch(I32|I64, cases, default Edge)`, `Return(values)`, `TailCall(SemanticCall)`, or `Trap(StructuredReason)`. Switch cases carry explicit integer bits and edges. Return and tail call match their signatures exactly. Normal calls remain instructions. There is no separate unreachable terminator or speculative invoke. Compare, zero, immediate, fallthrough, jump-table, raw-payload, and PC-relative forms belong downstream. Terminator metadata belongs to the block's terminator record.
- 2026-07-15: Canonical collections are mutated only through function-owned builder or editor interfaces. Before changing state, a mutation atomically rejects foreign or deleted handles, duplicate instruction membership, ill-typed operation operands or results, invalid edge ownership or argument shape, and signature-mismatched return or tail calls with a structured error. It never aborts, silently ignores, or partially applies invalid input. Missing terminators, temporary unreachable blocks, and temporary dominance violations may exist during a multi-step edit but cannot pass a whole-function verifier checkpoint. `finish()` verifies; Function remains mutable, and later mutation invalidates prior verification without introducing a frozen wrapper.
