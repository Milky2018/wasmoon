# ISS-451: Reuse one serial module compilation context

## Description

Wasmoon's serial compiler currently retains allocator scratch but recreates
optimizer analysis, lowering maps, target-analysis arrays, VCode builder
storage, and other per-function collections. AEGIS-128L compile time correlates
almost perfectly with surviving instruction count, indicating high repeated
per-entity allocation and reference-count traffic across all stages.

## Design

Introduce one module-compilation-owned context with package-private stage
storage. Each stage clears logical length while retaining safe flat capacity
across serial functions. Ownership must remain explicit: no globals, TLS caches,
or cross-module mutable sharing. Nested and concurrent compilers receive
independent contexts.

Only retain storage shown to be neutral or faster. Nested reference-backed
arrays and other shapes that regress due to copy-on-write or reference-count
behavior remain function-local.

## Acceptance Criteria
- [ ] One serial compilation context owns reusable MilkIR analysis, aegraph/GVN, selection, target-lowering, VCode, and regalloc scratch where ownership is safe.
- [ ] Large-small-large and nested-compiler tests prove that no stale state or capacity contents affect later functions.
- [ ] Concurrent compiler instances share no mutable compilation storage.
- [ ] Optimized IR, allocation vectors, code bytes, relocations, metadata, and runtime behavior remain unchanged.
- [ ] Seven cache-isolated AEGIS-128L runs materially improve module compilation beyond ISS-448 through ISS-450.
- [ ] The final guarded compile-only comparison reports serial Wasmoon and serial Wasmtime wall medians with parallel compilation disabled.
- [ ] Native, strict validation, formatting, warning-73, generated interfaces, and module-boundary gates pass.

## Notes
- 2026-08-29: Wasmtime v40's reusable `Context` retains function and analysis allocations between serial compilations. Wasmoon currently retains only the allocator session and environment at the target compilation seam.
- 2026-08-31: Seven fresh cache-isolated AEGIS-128L captures put compact
  Wasmoon module compilation at 94,198 us. Detailed captures report 33,817 us
  in regalloc, 18,623 us in optimization, 12,249 us in target lowering, 11,233
  us in semantic lowering, 7,710 us in frame planning plus emission, and 3,268
  us in frontend translation. Bundle allocation is 14,232 us: still important,
  but eliminating it completely would leave Wasmoon well above the 35,190 us
  median of nine serial, cache-disabled Wasmtime v40 compilations. The next
  experiment must therefore improve a pipeline-wide cost rather than another
  isolated availability query. Across the 63 functions, surviving instruction
  count correlates with semantic lowering at 0.977, target lowering at 0.981,
  and complete compilation at 0.935, reinforcing the per-entity pipeline-cost
  hypothesis.
- 2026-08-31: Low-overhead Wasmtime debug events attribute a median 2,973 us to
  translating all 63 Wasm functions and 31,342 us to compiling those functions
  plus 21 generated trampolines. Wasmoon functions 56 and 9 take 27,456 and
  13,253 us, while the corresponding Wasmtime functions take 9,145 and 4,280
  us. Those two functions alone account for about 27.3 ms, or 46 percent, of
  the 59.0 ms serial compile gap. This makes large-small-large context-reuse
  tests both a correctness requirement and the most useful first performance
  probe.
- 2026-08-31: Source inspection of Wasmtime v40 confirms that each reusable
  `CompilerContext` retains its `FuncTranslator`, Cranelift codegen `Context`,
  validator allocations, function storage, CFG, dominator tree, loop analysis,
  and `FunctionBuilderContext`; logical state is cleared before the context is
  returned to the pool. Wasmoon already shares immutable frontend module
  metadata and regalloc flat scratch, but still creates per-function optimizer
  analyses, semantic construction storage, target-analysis arrays, and VCode
  function storage. This is a source-backed explanation for a broad gap, not
  yet proof that every MoonBit container should be retained: prior nested-array
  reuse regressed, so each flat scratch family must earn its place in paired
  end-to-end measurements.
- 2026-08-31: Auditing the pending optimization experiments retained only the
  VCode builder change. `CheckedBuilder` now shares one pre-mutation operand
  validation path with `Builder`, and tie-id storage is allocated only for
  instructions that actually have tied outputs. The final mutation remains
  owned by `Builder`. Seven alternating cache-isolated AEGIS-128L pairs against
  `81b9571a` reduced the paired median module compilation time by 4,449 us,
  target lowering by 430 us, and VCode construction by 354 us. All 14 runs
  retained 56,840 code bytes, 272 spill slots, 306 spills, 1,131 reloads, and
  82 register moves. Capture: `_build/aegis-audit-vcode.jVCflF`.
- 2026-08-31: Two superficially allocation-reducing experiments were rejected.
  Reusing the dominance tree within one MilkIR `FunctionAnalysis` reduced its
  optimization-phase paired median by 170 us but regressed module compilation
  by 614 us (`_build/aegis-iss451-domtree-once.OoQY51kV`). Reusing verifier RPO
  as the sealed selection layout regressed module compilation by 1,477 us
  (`_build/aegis-iss451-zero-alloc-cfg.uhKMajFy`). Neither change retained
  storage across functions or met the issue's end-to-end performance rule, so
  both were removed instead of being committed as context reuse.
- 2026-09-01: Deferred while ISS-456 removes semantic MachV and changes the
  stage-ownership boundary. Reusable direct-lowering storage should be measured
  only after the replacement pipeline exists; preserving MachV-owned scratch
  for this issue would conflict with that architecture.
