## Description

`JITModule::load_with_imports` allocates executable code and publishes function-table entries incrementally, then invokes patch helpers that can abort. A later allocation, relocation, GC, unwind, or registration failure can therefore expose a partially installed module.

## Design

Implement the Wasmoon-owned `JitCodeInstaller` transaction selected by ISS-190. Validate and resolve all inputs before allocation, stage writable mappings and metadata, patch symbolically, register address-dependent metadata, transition to executable memory, and publish entry points only at commit. Return opaque installed-code ownership and roll back mappings and registrations on every failure.

## Acceptance Criteria
- [x] Installation returns structured resolution, allocation, relocation, protection, registration, and publication errors without aborting.
- [x] No function-table or module entry becomes visible before the full transaction commits.
- [x] Failure injection at each phase proves rollback and preserves any previous installation.
- [x] Live JIT objects and decoded artifacts enter the same installer seam and exhibit equivalent behavior.
- [x] Executable mappings follow platform RW-to-RX/MAP_JIT policy and flush instruction caches before publication.

## Notes
- 2026-07-22: The current loader sets import and function pointers while allocation is still in progress and ignores the boolean result of GC safepoint installation.
- 2026-07-22: Claimed after ISS-234 closed. The installer will return an opaque committed installation; `JITModule` publication remains the ISS-236 cutover, so this issue cannot expose partially staged addresses across the package boundary.
- 2026-07-22: Live artifacts now pass through the same compatibility and code-object verification function as decoded artifacts. `JitCodeInstaller` pre-resolves external/data symbols, stages every mapping, links against symbolic internal addresses, constructs address-bearing metadata, finalizes permissions and caches, and only then replaces its committed installation slot.
- 2026-07-22: Managed executable mappings now support explicit staging, finalization, and idempotent rollback. Windows uses RW then `PAGE_EXECUTE_READ` plus `FlushInstructionCache`; Linux uses RW then RX; macOS retains `MAP_JIT` and toggles per-thread JIT write protection before invalidating the instruction cache. The shared mapping registry is serialized across allocation, patching, release, and rollback.

## Close Notes

Closed with an opaque, stateful installer whose `current()` value changes only after the complete transaction commits. Structured fault injection covers resolution, allocation after a real staged mapping, relocation, metadata registration, protection, and publication; every failure returns the mapping count to its baseline and a failed replacement preserves the previous committed installation. Real unresolved-symbol and malformed entry-metadata failures are also covered, and live versus encoded/decoded artifacts produce the same complete installation snapshot.
