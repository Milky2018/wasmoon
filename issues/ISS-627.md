# ISS-627: Enforce coherent host resource budgets across runtime phases

## Description
Resource protection is fragmented across interpreter frame/slot limits, memory
and table declarations, component resource limits, HTTP buffering/timeouts, and
Core invocation controls. There is no coherent embedding policy covering guest
allocation, aggregate Store ownership, compilation work, and component compute.

At `25381fc7`, `runtime/table.mbt` permits sizes within the native representation
and grows a MoonBit Array without a host quota. Component native artifacts set
`cancellation_safepoints: false`. The HTTP server caps connections at 256 and
buffers/timeouts independently, which does not establish a guest CPU or total
memory budget. Core already has invocation controls; preserve those capabilities.

## Scope and Evidence
- Inventory linear memories, tables, GC objects, instances, handles/tasks,
  parked stacks, executable code, and retained compilation/cache storage.
- Distinguish per-object limits, aggregate ownership, logical size, committed
  bytes, and shared resources. Review parsing, validation, compilation,
  instantiation, execution, growth, and resource release as separate phases.
- CPU-only component loops and compiler complexity are required investigation
  cases; no new hang, OOM, or quantitative attack has been reproduced in this review.

## Design
Define the host's resource policy at an explicit ownership scope and apply it
before side effects or allocation. Connect supported compute cancellation and
deadline controls to Core and Component entry paths. Specify which work is
cooperatively bounded and any host callback or OS limits that cannot be covered.
Reuse existing limit mechanisms and keep guest-declared maxima distinct from
host policy.

## Acceptance Criteria
- [ ] Publish a resource/phase inventory with units, owner, admission check, release event, shared-resource accounting, and documented unsupported bounds.
- [ ] Embeddings can set meaningful memory/table/GC/instance/code and pending-work budgets for the supported ownership scopes.
- [ ] Boundary tests cover below/at/above quota, aggregate growth, shared resources, replacement, denial before side effects, rollback, and reuse after release.
- [ ] Tight compute loops in supported Core and Component engines obey a configured execution budget; cancellation releases parked work and a later invocation remains usable.
- [ ] Compilation and untrusted decoding have explicit supported bounds and structured exhaustion behavior, verified with representative adversarial shapes.
- [ ] Both-engine and cross-platform tests distinguish policy denial, ordinary traps, timeouts, and cancellation; documentation states the practical isolation limits.

## Notes
- 2026-10-14: ISS-624's [ownership inventory](../docs/evidence/iss624-runtime-gc-roots-2026-10-14/README.md) distinguishes reclaimed guest payloads from intentionally retained native object identity tombstones, canonical type graphs, module/artifact ownership, and allocator high-water capacity. Include these bytes and monotonic identifier limits in resource accounting/admission tests; do not equate zero unreachable guest roots with constant RSS. Auxiliary handle-only allocations also need a defined collection-pressure policy under aggregate budgets.
- 2026-10-14: This is a missing embedding capability and integration task, not a claim that every supported WebAssembly proposal mandates identical host quotas.
- Existing HTTP backpressure, connection limits, component slot limits, and interpreter budgets are useful safeguards; retain and integrate their established behavior.
