# ISS-627: Enforce coherent host resource budgets across runtime phases

## Metadata
- Type: feature
- Status: closed

- Labels: runtime, resources, embedding, component, jit, cancellation
- Assignee: unassigned
- Created: 2026-10-14
- Updated: 2026-10-16
- External ref: none

## Description
Resource protection is fragmented across interpreter frame/slot limits, memory
and table declarations, component resource limits, HTTP buffering/timeouts, and
Core invocation controls. There is no coherent embedding policy covering guest
allocation, aggregate Store ownership, compilation work, and component compute.

At `25381fc7`, `runtime/table.mbt` permits sizes within the native representation
and grows a MoonBit Array without a host quota. Component native artifacts set
`cancellation_safepoints: false`. The HTTP server caps connections at 256 and
buffers/timeouts independently, which does not establish a guest CPU or total
memory budget. Core already has invocation controls; preserve those capabilities.

## Scope and Evidence
- Inventory linear memories, tables, GC objects, instances, handles/tasks,
  parked stacks, executable code, and retained compilation/cache storage.
- Distinguish per-object limits, aggregate ownership, logical size, committed
  bytes, and shared resources. Review parsing, validation, compilation,
  instantiation, execution, growth, and resource release as separate phases.
- CPU-only component loops and compiler complexity are required investigation
  cases; no new hang, OOM, or quantitative attack has been reproduced in this review.

## Design
Define the host's resource policy at an explicit ownership scope and apply it
before side effects or allocation. Connect supported compute cancellation and
deadline controls to Core and Component entry paths. Specify which work is
cooperatively bounded and any host callback or OS limits that cannot be covered.
Reuse existing limit mechanisms and keep guest-declared maxima distinct from
host policy.

## Acceptance Criteria
- [x] Publish a resource/phase inventory with units, owner, admission check, release event, shared-resource accounting, and documented unsupported bounds.
- [x] Embeddings can set meaningful memory/table/GC/instance/code and pending-work budgets for the supported ownership scopes.
- [x] Boundary tests cover below/at/above quota, aggregate growth, shared resources, replacement, denial before side effects, rollback, and reuse after release.
- [x] Tight compute loops in supported Core and Component engines obey a configured execution budget; cancellation releases parked work and a later invocation remains usable.
- [x] Compilation and untrusted decoding have explicit supported bounds and structured exhaustion behavior, verified with representative adversarial shapes.
- [x] Both-engine and cross-platform tests distinguish policy denial, ordinary traps, timeouts, and cancellation; documentation states the practical isolation limits.
