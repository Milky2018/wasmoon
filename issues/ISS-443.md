# ISS-443: Allocate directly from flattened VCode

## Description

`machv_regalloc` currently materializes a complete `VCodeFunctionView` before
allocation. It copies layout, block parameters, instruction lists, successors,
edge arguments, operands, and clobbers into arrays of arrays even though VCode
already owns indexed and partly flattened forms of the same information.

The current aggregate difference between named allocation phases and
`regalloc_us` is only about 3 ms, so removing this adapter is a bounded
optimization rather than the complete register-allocation fix. It is also the
necessary interface boundary for a later dense, reusable allocation context.

## Design

Change the generic regalloc `FunctionView` contract from collection-returning
queries to count/index queries or non-owning indexed views. Implement that
contract directly over MachV VCode. Test-only views may use simple backing
arrays, but production must not construct a second nested representation.

Keep regalloc independent of MachV types and preserve the public allocation
result. Do not specialize the allocator for Wasmoon or either ISA.

## Acceptance Criteria
- [ ] Production allocation consumes VCode layout, CFG, operands, clobbers, and edge arguments without constructing arrays of arrays in `VCodeFunctionView`.
- [ ] The revised `FunctionView` remains implementable by standalone regalloc tests without importing MachV.
- [ ] Allocation plans, bundle-loop counters, spills, reloads, moves, per-function code sizes, and emitted AEGIS-128L code remain unchanged.
- [ ] ISS-441 metrics show the adapter construction cost removed rather than reassigned to an unmeasured phase.
- [ ] Regalloc and MachV adapter tests, strict allocation validation, formatting, warning-73, generated interfaces, and module-boundary gates pass.
