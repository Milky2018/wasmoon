# ISS-443: Allocate directly from flattened VCode

## Description

`machv_regalloc` currently materializes a complete `VCodeFunctionView` before
allocation. It copies layout, block parameters, instruction lists, successors,
edge arguments, operands, and clobbers into arrays of arrays even though VCode
already owns indexed and partly flattened forms of the same information.

The current aggregate difference between named allocation phases and
`regalloc_us` is only about 3 ms, so removing this adapter is a bounded
optimization rather than the complete register-allocation fix. It is also the
necessary interface boundary for a later dense, reusable allocation context.

## Design

Change the generic regalloc `FunctionView` contract from owning collection
queries to non-owning indexed views. Normalize MachV VCode once into flat tables
and offset vectors because VCode and generic regalloc deliberately own distinct
model types. Test-only views may use simple backing arrays, but production must
not construct a second nested representation or dispatch once per element.

Keep regalloc independent of MachV types and preserve the public allocation
result. Do not specialize the allocator for Wasmoon or either ISA.

## Acceptance Criteria
- [x] Production allocation consumes VCode layout, CFG, operands, clobbers, and edge arguments without constructing arrays of arrays in `VCodeFunctionView`.
- [x] The revised `FunctionView` remains implementable by standalone regalloc tests without importing MachV.
- [x] Allocation plans, bundle-loop counters, spills, reloads, moves, per-function code sizes, and emitted AEGIS-128L code remain unchanged.
- [x] ISS-441 metrics show the nested adapter construction cost removed rather than reassigned to an unmeasured phase.
- [x] Regalloc and MachV adapter tests, strict allocation validation, formatting, warning-73, generated interfaces, and module-boundary gates pass.

## Notes
- 2026-08-28: This issue intentionally makes no large wall-time claim. Current evidence puts its direct opportunity near 3 ms; its architectural value is enabling ISS-444 without retaining two competing function representations.
- 2026-08-28: Work started from the post-ISS-447 seven-run baseline. Median
  aggregate register allocation is 53,060 us: 25,325 us in bundle allocation,
  7,465 us in operand assignment, 5,791 us in live ranges, and 1,889 us in
  `function_view`. The adapter is not the dominant remaining phase, but its
  duplicate nested representation blocks the dense reusable context planned by
  ISS-444.
- 2026-08-28: Two measured count/index prototypes were rejected. Direct VCode
  queries raised aggregate regalloc to 74,971 us through repeated conversion and
  dynamic dispatch; flat cached count/index queries still took 71,242 us because
  they dispatched per element. The retained contract returns read-only
  `ArrayView` spans into flat tables, preserving one dispatch per logical span.

## Close Notes
- 2026-08-28: Replaced nested arrays with flat tables and offset vectors, split
  generic input validation from adapter timing, and retained standalone generic
  views. Across seven cache-isolated AEGIS-128L captures, median module compile
  time fell from 121,240 to 120,362 us and regalloc from 53,060 to 51,725 us.
  Adapter plus validation fell from the mixed 1,889 us baseline to 1,296 us;
  live ranges, bundle allocation, and operand assignment did not absorb the
  removed work. All seven runs have identical loop counters, allocation-edit
  vectors, and code-size vectors; the 59,428-byte artifact remains byte-identical
  with SHA-256 `0c31ca17b8f04e9ecd0022eb185d367d7027d197ba83f87cd762a8e2f4639840`.
  Native and strict-validation suites both pass 2,682/2,682, and the module
  boundary audit passes. Detailed evidence is in
  `docs/perf/aegis-flat-vcode-regalloc-2026-08-28.md`.
