# ISS-191: Choose package and public API boundaries

## Question

Which MoonBit packages should own MachV, the generic Target VCode shell, AArch64 and AMD64 instructions, target lowering, regalloc adapters, emitters, and Wasmoon orchestration, and which APIs must be public for downstream reusable-module consumers?

## Acceptance Criteria

- [ ] Package dependencies obey the reusable-infrastructure hard boundary.
- [ ] Public APIs are narrow, named by the agreed domain language, and do not expose construction-only or target-union compatibility surfaces.
- [ ] Expected breaking-version consequences are identified for later release planning.

## Notes
- 2026-07-15: Package names are decisions; existing names such as `machv_emit` and `machv_regalloc` are not assumed to survive unchanged.
- 2026-07-16: Claimed for a HITL architecture decision session using the established one-ticket discipline with domain modeling, deep-module interface analysis, grilling, and Markdown issue tracking. Current package names and interfaces will be treated as evidence rather than constraints, and no production migration will occur while this ticket is open.
- 2026-07-16: Decided on vertical machine-target ownership. `Milky2018/aarch64_target` and `Milky2018/x64_target` are reusable modules that each own their closed target instruction type, MachV-to-Target-VCode lowering, ABI and call layouts, target legality, allocation verification, frame planning, emission, and target-owned verifier checkpoints. Shared compiler modules provide only target-neutral MachV and Target VCode storage, the generic register-allocation algorithm and its Target VCode adapter, and generic unlinked-code and metadata contracts; they never import a concrete target. The current cross-ISA `machv/isa` union and `machv_emit` module are migration sources, not future seams. A later RISC-V target adds a third vertical module without modifying the AArch64 or AMD64 modules or introducing a target opcode union.
- 2026-07-16: Decided that semantic MachV, the generic Target VCode shell, and generic unlinked-code contracts remain one published `Milky2018/machv` module rather than creating a lockstep `target_vcode` module. Its supported package seams are the root semantic IR and verifier, `Milky2018/machv/vcode` for typed dense VCode and allocation facts, and `Milky2018/machv/code_object` for ordinary unlinked bytes, symbolic relocations, and target-neutral metadata. Construction-oriented `machv/block` and `machv/instr`, the concrete-target `machv/isa` union, and the mixed-ownership `machv/abi` package do not remain supported downstream interfaces. Logical call facts move to semantic MachV, physical ABI and register or frame types move to each machine-target module, and Wasmoon embedding and VMContext contracts remain in `wasmoon_jit`. This consolidation is a breaking `machv` interface change and therefore requires a minor version when implemented.
- 2026-07-16: Decided to retain `Milky2018/machv_regalloc` as the one independently published adapter between generic `Milky2018/machv/vcode` data and the target-independent `Milky2018/regalloc` algorithm. Its supported interface is limited to allocating a VCode function under an explicit allocation environment and verifying the resulting allocation; `Allocation` and its structural binding data belong to `machv/vcode`, while allocator-specific liveness, bundle, spill, planner, edit-builder, and statistics types remain implementation details. Each machine-target module wraps this adapter and adds its own physical-register, reserved-role, scratch, callee-save, and frame checks. Frame planning and `AArch64StackFrame` do not belong in the adapter. The adapter earns a separate seam because both native target modules reuse it without making `machv` depend on one allocator implementation. Removing the current broad surface is a breaking `machv_regalloc` interface change and requires a minor version when implemented.
- 2026-07-16: Decided that each machine-target module has exactly one supported root package, `Milky2018/aarch64_target` or `Milky2018/x64_target`. Target implementation is split across files in that package so opcode constructors, legalization helpers, ABI planners, register tables, frame mutation, and byte encoders can remain package-private instead of becoming importable cross-package declarations. The root exposes a deep whole-target `compile` entry for ordinary consumers plus the named `lower`, `allocate`, `plan_frame`, and `emit` checkpoint transformations and their explicit verifiers for compiler consumers. Target instruction and frame types are abstract where they must cross checkpoints. There is no public target trait, target union, generic target object, or construction-oriented subpackage. Consolidating the current target helpers and replacing their MilkIR-to-MachV facade is a breaking minor change for both target modules.
- 2026-07-16: Decided that `Milky2018/milkir_machv` retains only two supported package seams: its root owns core and explicit dialect-aware MilkIR-to-MachV lowering, structured errors, and small target-neutral policy; `Milky2018/milkir_machv/adapter` exposes only the semantic construction interface required by a dialect adapter to read mapped MilkIR values and emit target-neutral MachV values, blocks, edges, calls, traps, and opaque external-symbol identities. A WebAssembly adapter owns opcode decoding, contextual module-type validation, and WebAssembly runtime-operation requirements, but it cannot observe a product's VMContext offsets or runtime-symbol names, physical registers, scratch roles, target ISA, ABI layouts, target instructions, or mutable MachV storage internals. The current broad `/lower` context and `/lower/peephole` packages are migration sources, not supported interfaces; optimization placement remains for ISS-189. This is a breaking `milkir_machv` interface change and requires a minor version when implemented.
- 2026-07-16: Decided that `Milky2018/wasmoon_jit` has two supported package seams. The native root is the deep product facade exposing the configured JIT compiler and module compilation, versioned JIT ABI contract, artifact loading, code installation and installed-code ownership, structured pipeline or artifact or installation errors, and only the runtime operations needed by Wasmoon. `Milky2018/wasmoon_jit/artifact` is a target-portable package that owns only the Cwasm wire model plus bounded encoding and decoding into untrusted ordinary artifact data; it neither verifies target code nor installs it. The root performs compatibility and target Code Object verification. Raw C and assembly declarations, executable-memory primitives, relocation patch helpers, runtime-helper address getters, trampoline encoders, and GC, trap, unwind, or debug registration ordering remain root implementation details; the current public `/jit_ffi` package disappears. JIT metrics are configuration and result data on the root compiler seam, while CLI presentation leaves the module, so `/perf` is not a supported package. The standard WebAssembly binary encoder currently mixed into `/cwasm` moves to reusable `Milky2018/wasm_core/encoder`, while `/cwasm` becomes `/artifact`. These changes require minor versions for `wasmoon_jit` and `wasm_core`.
- 2026-07-16: Decided to replace `Milky2018/wasm_isa_lower` with the reusable single-package module `Milky2018/wasm_machv`. It validates contextual WebAssembly dialect contracts and translates WebAssembly-specific MilkIR extensions into target-neutral MachV exclusively through `milkir_machv/adapter`. It owns WebAssembly meanings for memory, tables, GC, exceptions, indirect calls, and the semantic runtime capabilities they require, but receives concrete VMContext semantic fields, opaque runtime-symbol identities, trap identities, and embedding call contracts through a narrow environment supplied by the embedding product. `wasmoon_jit` owns the Wasmoon environment implementation and its actual layout or symbol facts; neither reusable module imports `wasmoon_jit`. The old module is retired without a compatibility wrapper. Introducing `wasm_machv` is a new minor release, the corresponding `wasmoon_jit` adapter participates in its breaking minor, and an unchanged `wasm_milkir` interface needs only a patch if its dependency metadata changes.
- 2026-07-16: Decided on a mandatory Wasmoon production dependency funnel. Runtime, instantiation, and CLI run packages may enter native compilation only through the `wasmoon_jit` root and must not import `machv`, `machv_regalloc`, `milkir_machv`, `wasm_machv`, `aarch64_target`, or `x64_target` directly. This makes target selection, the mandatory pipeline, ABI supply, artifact verification, and installation ordering impossible to reassemble or bypass in product code. A separately named Wasmoon diagnostics package is the sole explicit exception: `explore` and compiler inspection tools may consume reusable checkpoint interfaces to render MilkIR, MachV, Target VCode, Allocation, frame, and code-object stages, but runtime, instantiation, and CLI run packages may not import that diagnostics package. The module-boundary audit must enforce both reusable-to-product isolation and the product funnel with a closed package allowlist rather than wildcard exceptions. This is an internal Wasmoon package reorganization; externally visible runtime interface changes, if any, are handled by the later migration and release ticket.
