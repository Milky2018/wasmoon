## Question

Which MoonBit packages should own MachV, the generic Target VCode shell, AArch64 and AMD64 instructions, target lowering, regalloc adapters, emitters, and Wasmoon orchestration, and which APIs must be public for downstream reusable-module consumers?

## Acceptance Criteria

- [ ] Package dependencies obey the reusable-infrastructure hard boundary.
- [ ] Public APIs are narrow, named by the agreed domain language, and do not expose construction-only or target-union compatibility surfaces.
- [ ] Expected breaking-version consequences are identified for later release planning.

## Notes
- 2026-07-15: Package names are decisions; existing names such as `machv_emit` and `machv_regalloc` are not assumed to survive unchanged.
- 2026-07-16: Claimed for a HITL architecture decision session using the established one-ticket discipline with domain modeling, deep-module interface analysis, grilling, and Markdown issue tracking. Current package names and interfaces will be treated as evidence rather than constraints, and no production migration will occur while this ticket is open.
- 2026-07-16: Decided on vertical machine-target ownership. `Milky2018/aarch64_target` and `Milky2018/x64_target` are reusable modules that each own their closed target instruction type, MachV-to-Target-VCode lowering, ABI and call layouts, target legality, allocation verification, frame planning, emission, and target-owned verifier checkpoints. Shared compiler modules provide only target-neutral MachV and Target VCode storage, the generic register-allocation algorithm and its Target VCode adapter, and generic unlinked-code and metadata contracts; they never import a concrete target. The current cross-ISA `machv/isa` union and `machv_emit` module are migration sources, not future seams. A later RISC-V target adds a third vertical module without modifying the AArch64 or AMD64 modules or introducing a target opcode union.
- 2026-07-16: Decided that semantic MachV, the generic Target VCode shell, and generic unlinked-code contracts remain one published `Milky2018/machv` module rather than creating a lockstep `target_vcode` module. Its supported package seams are the root semantic IR and verifier, `Milky2018/machv/vcode` for typed dense VCode and allocation facts, and `Milky2018/machv/code_object` for ordinary unlinked bytes, symbolic relocations, and target-neutral metadata. Construction-oriented `machv/block` and `machv/instr`, the concrete-target `machv/isa` union, and the mixed-ownership `machv/abi` package do not remain supported downstream interfaces. Logical call facts move to semantic MachV, physical ABI and register or frame types move to each machine-target module, and Wasmoon embedding and VMContext contracts remain in `wasmoon_jit`. This consolidation is a breaking `machv` interface change and therefore requires a minor version when implemented.
- 2026-07-16: Decided to retain `Milky2018/machv_regalloc` as the one independently published adapter between generic `Milky2018/machv/vcode` data and the target-independent `Milky2018/regalloc` algorithm. Its supported interface is limited to allocating a VCode function under an explicit allocation environment and verifying the resulting allocation; `Allocation` and its structural binding data belong to `machv/vcode`, while allocator-specific liveness, bundle, spill, planner, edit-builder, and statistics types remain implementation details. Each machine-target module wraps this adapter and adds its own physical-register, reserved-role, scratch, callee-save, and frame checks. Frame planning and `AArch64StackFrame` do not belong in the adapter. The adapter earns a separate seam because both native target modules reuse it without making `machv` depend on one allocator implementation. Removing the current broad surface is a breaking `machv_regalloc` interface change and requires a minor version when implemented.
