## Question

How should Wasmoon select a target, provide embedding and runtime information, invoke the mandatory MilkIR-to-MachV-to-Target-VCode pipeline, resolve symbols, install native code, and own Cwasm or cache artifacts without leaking product concepts into reusable modules?

## Acceptance Criteria

- [ ] The Wasmoon-owned orchestration API and reusable compiler APIs have explicit ownership boundaries.
- [ ] Runtime symbols, VMContext layout, executable memory, traps, stack maps, and code installation each have one owner.
- [ ] The decision states whether any persisted artifact contains MachV, Target VCode, or only emitted code and metadata.

## Notes
- 2026-07-15: Every AArch64 and AMD64 native JIT compilation must pass through MachV.
- 2026-07-16: Claimed for a HITL architecture decision session using the established Wayfinder one-ticket discipline with grilling, domain modeling, deep-module interface analysis, and Markdown issue tracking. No production implementation will occur while this ticket is open for design.
- 2026-07-16: Decided that live JIT compilation and Cwasm loading converge at the `Unlinked Code Object` seam. Cwasm and every persistent code cache contain only target machine bytes, symbolic runtime and function relocations, Wasmoon module identity, GC, trap, unwind, debug, and compatibility metadata. They never serialize MilkIR, MachV, Target VCode, Allocation, FrameLayout, resolved process addresses, executable-memory addresses, or linked images. Wasmoon JIT resolves symbols and installs code only after loading the artifact into the current process. The present `CwasmArtifact::from_jit_plan` resolution-before-serialization path is migration debt because serialization discards the resolved addresses.
