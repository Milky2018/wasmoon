## Question

How should Wasmoon select a target, provide embedding and runtime information, invoke the mandatory MilkIR-to-MachV-to-Target-VCode pipeline, resolve symbols, install native code, and own Cwasm or cache artifacts without leaking product concepts into reusable modules?

## Acceptance Criteria

- [ ] The Wasmoon-owned orchestration API and reusable compiler APIs have explicit ownership boundaries.
- [ ] Runtime symbols, VMContext layout, executable memory, traps, stack maps, and code installation each have one owner.
- [ ] The decision states whether any persisted artifact contains MachV, Target VCode, or only emitted code and metadata.

## Notes
- 2026-07-15: Every AArch64 and AMD64 native JIT compilation must pass through MachV.
- 2026-07-16: Claimed for a HITL architecture decision session using the established Wayfinder one-ticket discipline with grilling, domain modeling, deep-module interface analysis, and Markdown issue tracking. No production implementation will occur while this ticket is open for design.
- 2026-07-16: Decided that live JIT compilation and Cwasm loading converge at the `Unlinked Code Object` seam. Cwasm and every persistent code cache contain only target machine bytes, symbolic runtime and function relocations, Wasmoon module identity, GC, trap, unwind, debug, and compatibility metadata. They never serialize MilkIR, MachV, Target VCode, Allocation, FrameLayout, resolved process addresses, executable-memory addresses, or linked images. Wasmoon JIT resolves symbols and installs code only after loading the artifact into the current process. The present `CwasmArtifact::from_jit_plan` resolution-before-serialization path is migration debt because serialization discards the resolved addresses.
- 2026-07-16: Decided that every Cwasm or persistent-cache artifact carries a strict compatibility manifest containing the format version; target architecture, operating-system ABI, endianness, and pointer width; required CPU feature set; one Wasmoon JIT ABI version covering the internal calling convention, VMContext layout, persistent roles, runtime-symbol contract, traps, GC, stack maps, and unwind; a code-generation revision; the source module and semantic-feature digest; and compilation policy including optimization level and code model. All fields match exactly except that the host CPU feature set may be a superset. A cache mismatch is a cache miss and recompiles; an explicitly loaded incompatible Cwasm returns structured `ArtifactIncompatible`. Missing or unknown fields are rejected rather than guessed, and the manifest never contains runtime addresses.
- 2026-07-16: Decided that Wasmoon's production compilation seam is one product-owned `JitCompiler`, configured once with an explicit target specification, platform ABI, required CPU features, code model, optimization policy, and Wasmoon JIT ABI. A host constructor performs host detection only at the product edge; explicit-target construction supports Cwasm generation, and unsupported or unknown targets fail structurally without a fallback. `compile_function` accepts verified MilkIR plus minimal Wasmoon function identity, internally supplies canonical VMContext, internal ABI, runtime-symbol identity, trap, and GC contracts, forces the complete MilkIR-to-MachV-to-static-Target-VCode-to-allocation-to-frame-to-emission pipeline, and returns an `Unlinked Code Object`. Parsing, Wasm validation, instantiation, runtime address resolution, executable memory, and installation remain outside. Reusable stage interfaces remain available, but Wasmoon production paths do not assemble them manually. Target dispatch occurs once at product orchestration and stays statically specialized downstream.
- 2026-07-16: Decided that one Wasmoon-owned `JitCodeInstaller` transaction installs a complete function set or replacement. It validates manifests and code objects, resolves every runtime, module-function, and import target before allocation, allocates non-executable writable memory, copies and patches all relocations and fixups, constructs and registers address-dependent trap, GC, stack-map, unwind, debug, and address-range metadata, transitions memory to read-only executable form, flushes instruction caches, and publishes function-table entries and module entry points only as the final atomic commit. Failure rolls back mappings and registrations without changing the previously visible function table. `JIT FFI` owns only platform memory-protection, cache-flush, and registration primitives; the installer owns ordering, rollback, and structured `JitInstallError`. Its opaque `InstalledCode` result owns code memory and metadata-registration lifetimes. Linux and Windows use RW-to-RX transitions; macOS uses `MAP_JIT` with thread write protection. Recompilation uses the same transaction and atomically swaps the entry only after the replacement is complete.
- 2026-07-16: Decided that one versioned Wasmoon JIT ABI contract is the product's sole source for the existing internal call contract plus VMContext field layout, runtime-symbol identities and semantics, native trap numbers and payload encoding, GC stack-map encoding, unwind contract, and persistent runtime roles. MoonBit compiler code and C/assembly JIT glue must derive their constants from one schema or prove exact agreement with compile-time assertions; no parallel handwritten offset or code tables remain. Wasmoon Runtime owns VMContext instances and their memory, table, global, and Store state, but not the ABI schema. The `JitCodeInstaller` alone resolves current symbol addresses and registers address-dependent trap, stack-map, unwind, debug, and range metadata. `JIT FFI` implements only platform primitives. Reusable compiler modules consume generic ABI data, opaque external identities, and generic safepoint/location records. Any incompatible contract change increments `jit_abi_version`, and the compiler and installer must use the same contract version.
- 2026-07-16: Decided that `JitCompiler` is reusable across modules, while each validated Wasm module creates one immutable `ModuleCompilation` context containing its module and semantic-feature digest, stable function and import identities, complete function signatures, VMContext/module layout, and the module portion of the compatibility manifest. Its single compilation primitive independently compiles one function index and verified MilkIR function into one `Unlinked Code Object`; failure exposes no partial object and does not mutate the context. Lazy JIT, tiered recompilation, eager compilation, and Cwasm generation all call this same primitive. Module-wide compilation is only iteration and aggregation over it. Code objects use stable function identities without depending on whether referenced functions are compiled or installed. The context contains no Store, VMContext instance, executable memory, runtime address, or serialized compiler IR.
