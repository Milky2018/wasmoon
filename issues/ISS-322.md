# ISS-322: Release native continuation GC frames exactly once

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: jit, continuation, gc, cancellation, trap, lifecycle, safety, agent
- Assignee: codex
- Created: 2026-07-29
- Updated: 2026-07-29
- External ref: none

## Description
`JITCallContinuation::advance` begins one context-local GC frame before the
first native entry. The normal return path ends that frame, but trap, exit,
cancellation, and context-loss paths terminate the continuation without
ending it. After a trap the allocated `wasmoon_gc_frame_t` remains linked to
the JIT context; parked cancellation instead strands the frame in the
detached activation while releasing that activation's fiber stack.

This violates the exact-once terminal lifecycle required by ISS-308 and
ISS-311. It can also leave stale safepoint metadata at the head of the frame
chain and cause a later continuation to pop the wrong frame.

## Design
Track GC-frame ownership independently from first-entry and active state.
Route every terminal transition through one idempotent cleanup method that
ends the frame if and only if this continuation began it, then clears
temporary safepoint and root-scratch state. Suspension retains the frame.

Add a native diagnostic seam for deterministic live-frame assertions and
exercise both trap and cancellation after suspension. Do not rely on eventual
JIT-context destruction or sanitizer-only leak detection.

## Acceptance Criteria
- [x] A suspended continuation owns exactly one active GC frame.
- [x] Normal return, trap/exit, and cancellation end the owned frame exactly once.
- [x] Repeated terminal operations cannot pop another continuation's frame.
- [x] Trap and cancellation regressions directly observe the live frame count.
- [x] Targeted JIT tests and repository quality gates pass.
