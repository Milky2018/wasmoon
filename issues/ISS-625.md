# ISS-625: Return recoverable failures across public runtime and native boundaries

## Description
Recoverable input, capacity, or host failures can become process termination
when public runtime paths use `try!`, `abort`, or equivalent native fatal paths.
Audit error propagation across the public runtime and FFI rather than fixing
only the memory constructor reported below.

At `25381fc764c47e805f318012c272fdd51f62c57f`, the module
`(module (memory i64 281474976710656))` passes the current validator.
`Memory::from_type` rejects its minimum before allocation because it exceeds
the native size representation. `instantiate_module_with_init` calls
`instantiate_module`, whose `try! Memory::from_type` terminates the host with
SIGABRT. An outer runtime-error catch cannot intercept it. The issue is failure
containment; allocating this enormous memory is not an acceptance requirement.

## Scope and Evidence
- Cover public parsing/validation, instantiation, allocation/growth, invocation,
  host callback, artifact installation, and close/cancel error paths.
- Classify fatal operations by reachable cause: malformed input, runtime trap,
  resource denial, native allocation failure, host I/O failure, or an internal
  invariant guaranteed by a protected interface.
- Use [the valid-module capacity reproduction](../docs/evidence/runtime-quality-2026-10-14/README.md). The separate invalid-type reproduction deliberately violates the current low-level validation precondition and is interface-hardening evidence for ISS-626.

## Design
Propagate recoverable conditions as typed errors/results through MoonBit and
native status mappings. Preserve distinct guest traps, host exits, cancellation,
and allocation failures. Keep genuinely unreachable internal invariant checks
only where their preconditions are enforced and documented. Review source and
behavior manually; fatal-symbol counts are not proof of correctness.

## Acceptance Criteria
- [ ] Record an error-path inventory with disposition and protected precondition for retained fatal operations.
- [ ] The valid memory64 capacity case returns a structured instantiation failure without aborting; the same process can instantiate and run another valid module afterward.
- [ ] Exercise recoverable memory/table/GC/code allocation failures, growth denial, invalid arguments, and native host failures at their public entry points.
- [ ] Failed operations roll back owned resources and leave subsequent operations safe; both engines preserve the intended error category where applicable.
- [ ] Native C boundaries report recoverable failures without unwinding unsafely through foreign callbacks or misclassifying them as guest unreachable.
- [ ] Relevant native, strict C, external, and sanitizer checks pass; closure covers the reviewed class rather than only the reported `try!` call.
