# ISS-356: Enforce exclusive WASI host context ownership

## Metadata

- Status: closed

- External ref: none

## Description
`wasi_command_component_host` captures a `WasiComponentCtx` without claiming
exclusive ownership, and `ComponentHostInstaller` can be installed more than
once. Installer or context aliases can therefore make two runtimes share the
same reactor, descriptors, resources, and close lifecycle.

## Design
Make every component host installer single-consumption. Store an exclusive,
terminal runtime-owner claim in `WasiComponentCtx` so separately-created
installers also contend on the same state. Acquire both claims before linker
mutation, and only grant close authority after both claims succeed.

## Acceptance Criteria
- [x] Reusing one installer in a second runtime is rejected before mutation.
- [x] Installing two aliases made from one context is rejected before mutation.
- [x] A rejected installer cannot close resources owned by the first runtime.
- [x] Public black-box alias tests and component runtime suites pass.

## Close Notes

`ComponentHostInstaller` now carries shared single-consumption state and
separates ownership claim from linker population. `ComponentRuntime::install`
claims first, and only a successfully claimed installer can close its captured
resources. `WasiComponentCtx` stores a terminal owner claim shared by every
alias, so separately-created installers cannot bypass the installer guard.

The public black-box regression reproduced both aliases as accepted before the
fix. It now observes `HostInstallerAlreadyConsumed` and
`HostContextAlreadyOwned`, closes each rejected runtime, and successfully runs
the Preview 3 async stdin command through the original owners.

Verification passed with native tests at 2497/2497, Python tests at 60/60,
stable Component 0.2 at 23/23 files and 845 commands in both JIT and
interpreter modes, and Component 0.3 async at 24/24 files and 153 commands in
both modes.
