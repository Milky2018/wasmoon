## Description
`Function` currently permits a signature-only construction protocol in which declared parameters are not materialized in `Function.params`. Callers then assume that the first N calls to `new_value()` recreate the missing parameter values. This makes parameter identity implicit and allows printing, verification, optimization, and lowering to observe different function contracts.

## Design
Introduce a canonical signature-based constructor that eagerly creates explicit parameter values and result types, advances value allocation past those parameters, and exposes parameter lookup without requiring callers to guess value IDs. Lock the contract with focused red tests before implementation. Keep the legacy constructor temporarily so downstream producers can migrate without an intermediate broken tree.

## Acceptance Criteria
- [x] Signature-based construction eagerly materializes every declared parameter with the correct type and stable value ID.
- [x] The next allocated value ID follows the materialized parameters.
- [x] Callers can retrieve declared parameter values explicitly.
- [x] A derived signature matches the explicit parameter and result arrays.
- [x] Focused MilkIR tests cover the new contract.
