# ISS-397: A v128 in a GC object aborts the process when the JIT is on

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: jit, gc, simd, robustness, agent
- Assignee: unassigned
- Created: 2026-08-05
- Updated: 2026-08-05
- External ref: none

## Description
Six lines of valid WAT kill the process under the default configuration:

```wat
(module
  (type $s (struct (field v128)))
  (func (export "go") (result i32)
    (local $r (ref $s))
    (local.set $r (struct.new $s (v128.const i32x4 1 2 3 4)))
    (i32.const 7)))
```

`wasmoon test` exits **134 (SIGABRT)** with `V128 values not yet supported in
JIT` on **stdout** and nothing on stderr. The same module passes under
`--no-jit`, and `wasmoon run` returns `7`.

Four instruction paths reach it, each confirmed:

| Instruction | default | `--no-jit` |
| --- | --- | --- |
| `struct.new` with a v128 field | exit 134 | passes |
| `array.new` with v128 elements | exit 134 | passes |
| `struct.set` of a v128 field | exit 134 | passes |
| `array.set` of a v128 element | exit 134 | passes |

Scope is exactly the GC aggregates. v128 globals, and v128 function
parameters and results, are unaffected — both pass in both modes.

## Design
The JIT is not at fault, and that is the point. `wasm_machv/lower.mbt`
declines v128 correctly and by design, returning a reason string:

```moonbit
if !is_runtime_word_type(source_types[0]) {
  return Some(
    "the current Wasm GC runtime ABI cannot initialize arrays with v128 values",
  )
}
```

That bail-out works. The crash is *downstream of a successful bail-out*: the
function falls back to the interpreter, but `Store` hands the interpreter the
JIT's `CHeap` whenever the JIT is enabled, and `CHeap`'s encoding is narrower
than the `Value` domain it is being asked to encode.

```moonbit
pub fn value_to_i64(value : @types.Value) -> Int64 {
  match value {
    ...
    V128(_) => abort("V128 values not yet supported in JIT")  // c_heap.mbt:105
```

So the root cause is not a missing case. It is that `Store::alloc_struct`
selects the heap on *whether the JIT is enabled* rather than on *whether the
JIT compiled this function*, which lets interpreter-domain values reach an
encoder that cannot represent them.

The decode direction of the same encoding is worse, because it does not
abort:

```moonbit
V128 => I64(raw) // V128 not fully supported                  // c_heap.mbt:177
```

Reading a v128 field back yields `I64(0)` under the JIT and `Null` under
`--no-jit` — two different silently wrong answers for the same program. A
wrong answer from a runtime outranks a crash, so this half should be fixed
even if the abort is only contained.

Fixed by implementing the feature: the field slot becomes 16 bytes, so the
encoding is total and there is no case left to abort on or to answer with a
value of the wrong type.

```c
typedef struct GcSlot {
    int64_t lo;   // every non-v128 value, and the only word scanned for refs
    int64_t hi;   // a v128's high half; zero otherwise
} GcSlot;
```

The alternative -- packing fields by declared type -- was rejected. It keeps
the partiality (each site still has to ask "is this one a v128?") and it
duplicates the layout rule across the C heap, the encoder and the lowering,
which is the shape that produced this bug. Uniform slots cost memory and
remove the question.

The int64 accessors stay, addressing the low word, because JIT-emitted code
only ever produces runtime words. Callers that can hold a vector use the
`_wide` entry points beside them.

## Close Notes

Three separate defects, one cause. The GC runtime ABI encoded every value
into a single `int64_t`, and a v128 does not fit:

| | before | after |
| --- | --- | --- |
| store a v128 into a GC object | SIGABRT | works |
| read one back, JIT | `I64(0)` | the vector |
| read one back, `--no-jit` | `Null` | the vector |

The third was not the heap at all. `MarkSweepHeap` stores `Value` directly
and was always correct; `default_value_for_storage_type` sent v128 to a
`_ => Null // Default for other reference types` catch-all. A v128 is not a
reference type, and the comment shows nobody meant to include it.

The JIT was never at fault: it declined v128 aggregates by design and
returned a reason string. But `contains_unsupported_instruction` returns
false for everything, so declining is not an accepted outcome here -- the
WAST runner's strict mode turns it into a test failure. The bail-outs
therefore had to go rather than be relied on, and all six now lower.

Vectors cross the call boundary by address, through a caller-owned 16-byte
stack slot, because neither target's call lowering has a 128-bit return
convention and no call in the tree returns two registers. Adding one would
have been a much larger change to both backends for a rare path.

`gc_heap_mark` reads only a slot's low word. Every reference is encoded
there, so the high word holds nothing but vector payload and scanning it
could only invent false positives. Marking stays conservative either way --
an i64 field holding 4 was already indistinguishable from a reference to
object 2 -- which is sound because sweeping never moves an object and the
candidate decoder rejects anything outside the object table. So v128 payload
adds no new imprecision.

Verified: 2584/2584 native tests, spec corpus 258/258 files and 62563 tests
in both modes, `find_gc_bugs.py` clean, CLI behaviour tests pass. The 13 new
tests exercise get, set, fill, new, new_default, new_fixed and copy, a vector
between an i32, a reference and an i64, and a 200-node chain that collects
while vectors and references share objects. Under a 4 KiB heap with
`WASMOON_GC_VERIFY=1` and `WASMOON_GC_ASSERT_BARRIER=1`, so collection really
runs, they still pass in both modes.

`find_gc_bugs.py --fault-alloc-every 7` reports `fault non-pass: 3/17` both
before and after this change. Pre-existing, not investigated here.
