## Description
Complete native Windows readiness and verify it through the actual interpreter and JIT. The original Windows backend returned `ENOSYS`; the implementation now supports the descriptor kinds documented in [Windows native runtime](../docs/windows.md), while full runtime acceptance remains in progress.

The previous Windows JIT path did not implement readiness either: it slept for timers and could return success with zero events. Returning an explicit host error avoids that silent contract violation but does not provide feature parity.

## Design
Add a Windows-specific readiness adapter appropriate to each descriptor kind. Do not emulate all descriptors with a single busy loop: console input, regular files, pipes, and Winsock sockets have different readiness primitives. Keep subscription validation, clock handling, event ordering, and ABI encoding in the shared MoonBit implementation.

## Acceptance Criteria
- [ ] Windows native stdin, regular-file, pipe, and socket subscriptions have documented readiness behavior.
- [ ] Mixed clock/fd subscriptions return when the first event becomes ready and never return success with zero events.
- [ ] Interrupt, invalid-descriptor, hangup, and host-error cases map to structured WASIp1 results.
- [ ] Windows interpreter and JIT run the same poll conformance tests.

## Pre-implementation verification audit (2026-09-15)

At that audit, the issue remained deferred: modules/wasmoon/wasi/poll_native.c returned ENOSYS in its Windows wait branch (lines 86-94). The CI matrix then covered Linux AMD64 and macOS ARM64, not Windows. Passing POSIX P1 tests does not satisfy the Windows descriptor-kind or mixed-wait criteria.

## Implementation scope (2026-09-15)

The user explicitly requested the full Windows runtime port alongside readiness, with actual interpreter and JIT verification on native Windows CI. ISS-525 owns the prerequisite platform support. Standalone C-backend success is not sufficient to close this issue.

## Windows implementation progress

- 2026-09-15: Implemented a shared Windows backend using WSAPoll for sockets, non-consuming pipe quota queries, console input inspection, and immediate regular-file/NUL readiness. Synchronous pipes and consoles require sleeping rechecks bounded to 10 ms; this latency is explicit, not an event-driven guarantee. Added native Windows descriptor regressions; CI and guest dual-engine acceptance remain pending.

- 2026-09-15: Added six actual Wasm guest executions (both engines, pending clock, delayed pipe, regular file) that verify event count/userdata and binary reads after readiness. The harness passes on macOS; native Windows guest execution remains pending. Native Windows byte I/O now avoids CRT text translation.

- 2026-09-15: Windows CI 34926134832 passed six actual readiness guests and all component lanes in both engines. Expanded the guest runner to twelve executions, adding EOF, invalid guest descriptors and duplicate subscriptions; the expanded harness passes locally and invalid-fd errno was checked against Wasmtime. Documented descriptor behavior and the bounded 10 ms handle recheck latency. Windows native test compilation and complete external acceptance remain under ISS-525.
