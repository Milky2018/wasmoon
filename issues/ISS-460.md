# ISS-460: Preserve shared zero-extended indices in native address selection

## Description

The direct native selector folds a single-use `i32 -> i64` unsigned extension
into an indexed memory operation, but materializes the extension when the same
index feeds multiple otherwise foldable addresses. The selection legality
model already admits shared pointer bitcasts as zero-cost address nodes, yet
does not apply the same all-consumers rule to zero extension.

This leaves repeated `Convert(ExtendI32ToI64)`, `AddAddress`, and zero-offset
load/store operations in wide straight-line kernels. Against the accepted
ISS-433 controls, current AArch64 code is 7,104 bytes instead of 6,768 for
`generichash2` function 27 and 4,860 bytes instead of 3,980 for `core3`
function 48. The regression first appeared with direct MilkIR-to-VCode
streaming; the canonical DFG optimizer subsequently improved both controls
relative to the immediate pre-DFG pipeline but cannot repair target address
selection.

## Design

Treat a verified unsigned `i32 -> i64` extension as a zero-cost address node
only when every use is consumed by a legal indexed memory selection. Keep the
decision in target-neutral native selection because both AArch64 and x64 can
consume a zero-extended 32-bit index without a standalone conversion. Do not
delete or defer an extension that has any non-address use.

Add focused tests for multiple load/store consumers and for a mixed address
plus arithmetic use. Retain the canonical DFG and direct target pipeline; do
not restore semantic MachV or add a target-specific workload exception.

## Acceptance Criteria
- [ ] Multiple indexed memory consumers share one unsigned-extended index without emitting a standalone conversion or pointer addition.
- [ ] A shared unsigned extension with any non-address use remains materialized and mapped correctly.
- [ ] AArch64 BLAKE2b and Salsa20 hot-function code returns to the accepted controls without worsening allocation pressure.
- [ ] The same target-neutral selection behavior is covered by x64 lowering tests.
- [ ] MilkIR/native selection, both targets, JIT/interpreter differential, strict allocation validation, warning-73, generated-interface, formatting, and module-boundary gates pass.

## Notes
- 2026-09-03: Seven current AEGIS-128L captures already satisfy the allocator thresholds: aggregate bundle allocation has a 9,929 us median and function 56 complete regalloc has a 7,276 us median. The remaining P0 blocker is code-quality validation, which exposed this address-selection regression.
- 2026-09-03: A controlled build at `03759bce` records 6,768-byte BLAKE2b and 3,980-byte Salsa20 hot functions. The direct-streaming cut at `f3d5644d` inflated them to 10,792 and 9,444 bytes; subsequent work recovered much of that loss, reaching 7,104 and 4,860 bytes at `29f9129b`. Optimized MilkIR is now the same size or smaller than the old control, while allocated VCode contains repeated explicit extensions and address additions.
