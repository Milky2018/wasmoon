# ISS-460: Preserve shared zero-extended indices in native address selection

## Description

The direct native selector folds a single-use `i32 -> i64` unsigned extension
into an indexed memory operation, but materializes the extension when the same
index feeds multiple otherwise foldable addresses. The selection legality
model already admits shared pointer bitcasts as zero-cost address nodes, yet
does not apply the same all-consumers rule to zero extension.

This leaves repeated `Convert(ExtendI32ToI64)`, `AddAddress`, and zero-offset
load/store operations in wide straight-line kernels. Against the accepted
ISS-433 controls, current AArch64 code is 7,104 bytes instead of 6,768 for
`generichash2` function 27 and 4,860 bytes instead of 3,980 for `core3`
function 48. The regression first appeared with direct MilkIR-to-VCode
streaming; the canonical DFG optimizer subsequently improved both controls
relative to the immediate pre-DFG pipeline but cannot repair target address
selection.

## Design

Treat a verified unsigned `i32 -> i64` extension as a zero-cost address node
only when every use is consumed by a legal indexed memory selection and the
target explicitly reports that indexed memory lowering does not rematerialize
the extension and address addition. AArch64 has that capability. The current
x64 target does not, so it retains one shared extension instead of duplicating
it inside every indexed access. Do not delete or defer an extension that has
any non-address use.

Add focused tests for multiple load/store consumers and for a mixed address
plus arithmetic use. Retain the canonical DFG and direct target pipeline; do
not restore semantic MachV or add a target-specific workload exception.

## Acceptance Criteria
- [x] Multiple indexed memory consumers share one unsigned-extended index without emitting a standalone conversion or pointer addition on targets that can consume it directly.
- [x] A shared unsigned extension with any non-address use remains materialized and mapped correctly.
- [x] AArch64 BLAKE2b returns to its 6,768-byte control; Salsa20 remains within 3% of its 3,980-byte control with no worse allocation pressure.
- [x] Target capability behavior is covered by target-neutral selection tests and explicit AArch64/x64 lowering assertions.
- [x] MilkIR/native selection, both targets, JIT/interpreter differential, strict allocation validation, warning-73, generated-interface, formatting, and module-boundary gates pass.

## Notes
- 2026-09-03: Seven current AEGIS-128L captures already satisfy the allocator thresholds: aggregate bundle allocation has a 9,929 us median and function 56 complete regalloc has a 7,276 us median. The remaining P0 blocker is code-quality validation, which exposed this address-selection regression.
- 2026-09-03: A controlled build at `03759bce` records 6,768-byte BLAKE2b and 3,980-byte Salsa20 hot functions. The direct-streaming cut at `f3d5644d` inflated them to 10,792 and 9,444 bytes; subsequent work recovered much of that loss, reaching 7,104 and 4,860 bytes at `29f9129b`. Optimized MilkIR is now the same size or smaller than the old control, while allocated VCode contains repeated explicit extensions and address additions.
- 2026-09-03: An unconditional target-neutral fold was rejected because x64 currently expands each indexed access back into an extension and address addition. `TargetSink` now exposes the relevant capability: AArch64 enables the shared fold, while x64 preserves one shared extension. Focused tests lock both policies and the mixed arithmetic-use case.
- 2026-09-03: A broader attempt to classify shared complete address expressions as free was rejected and fully reverted. It introduced recursion between memory selection and shared-consumer classification and aborted real workloads. Shared unsigned extension is the bounded, non-recursive ownership rule retained here.
- 2026-09-03: Three final AArch64 captures record 6,768-byte BLAKE2b hot functions with 22 spills and 176 reloads, and a 4,072-byte Salsa20 hot function with 15 spills and 32 reloads. AEGIS-128L function 56 is 15,060 bytes with 73 spills and 506 reloads; aggregate bundle allocation has a 6,948 us median and function 56 complete regalloc has a 5,404 us median. All four workload runs completed successfully.

## Close Notes

Closed after making shared unsigned-index folding conditional on an explicit
target lowering capability. The selector now removes the shared extension only
when every consumer is a legal indexed address and the target consumes that
index without recreating the discarded operations. Mixed uses and x64 retain
the shared definition. Native tests pass 2215/2215 with
`VCODE_REGALLOC_VALIDATION=1`; warning-73, generated interfaces, formatting,
and the module-boundary audit also pass.
