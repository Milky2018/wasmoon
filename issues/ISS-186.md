## Question

What data and services cross from MachV into target-owned lowering, and what generic Target VCode interface lets AArch64 and AMD64 own instructions, addressing modes, physical constraints, and target legality without duplicating shared CFG infrastructure?

## Acceptance Criteria

- [ ] The resolution specifies the input, output, errors, ownership, and mutability of target lowering.
- [ ] Target-specific instruction types cannot appear in MachV or in another target's VCode.
- [ ] The shared Target VCode shell is deep enough for regalloc and emission without becoming another union dialect.

## Notes
- 2026-07-15: The standing direction is one generic Target VCode shell parameterized by independent target instruction types.
- 2026-07-15: Claimed for a HITL Wayfinder decision session using grilling, domain modeling, and deep-module interface analysis.
- 2026-07-15: Decided that target lowering is an all-or-nothing operation. Success returns a complete target-specific `VCodeFunction[TargetInst]` that owns its blocks, values, and instructions, shares no mutable aliases with MachV, and has passed target legality, legalization, and the Target VCode verification checkpoint. Failure returns a structured lowering error and exposes no partial builder state. The result is not permanently frozen; later mutation requires revalidation.
- 2026-07-15: Decided that each target lowering context contains only immutable target facts and compile policy, such as CPU features, tuning choices, and code model. AArch64 and AMD64 own statically typed contexts; lowering does not use a shared ISA union, dynamic dispatch, arbitrary callbacks, or a service locator. Runtime symbol resolution, executable memory, register allocation, and emission do not cross this seam; symbolic identities remain unresolved until linking. ABI inputs are deferred to ISS-187.
- 2026-07-15: Performance is a primary constraint, not a justification for extra abstraction. Target lowering must permit direct target-owned pattern matching, compact data, linear construction, and compile-time specialization without per-instruction dynamic dispatch.
- 2026-07-15: Decided that each target owns whole-function traversal, instruction selection, local pattern fusion, and legalization. The shared layer provides compact generic Target VCode storage, dense handles, a typed builder, and invariant checks rather than a per-op visitor or lowering trait. Implementations preallocate from MachV block and value counts and use dense O(1) maps; the common path should remain near-linear, while target-owned bounded analyses or extra passes require a concrete optimization benefit.
- 2026-07-15: Decided that lowering failures are structured and target-owned. They identify the lowering phase, MachV function/block/instruction site, and reason; unsupported valid operations, invalid input, and invalid output are explicit failures rather than aborts, silent omission, or placeholder code. AArch64 and AMD64 use separate closed error types, which Wasmoon JIT maps into its pipeline error at the orchestration boundary. Detailed verifier error categories remain with ISS-188.
- 2026-07-15: Decided that the public seam consists of separate static target entry points returning `VCodeFunction[AArch64Inst]` and `VCodeFunction[AMD64Inst]`. Wasmoon JIT branches once at orchestration, after which lowering, register allocation, and emission remain statically typed. There is no runtime target union or `TargetLowerer` trait; a future RISC-V target adds another entry point and orchestration branch.
- 2026-07-15: Decided that lowering borrows an already verified MachV function without cloning it and consumes it through read-only dense-indexed queries. It must not mutate the input or retain references into MachV-owned collections. A private mutable typed builder creates independent Target VCode storage; success returns ordinary mutable Target VCode rather than a frozen wrapper, and later mutation requires revalidation.
- 2026-07-15: Decided that production Target VCode stores register-allocation facts once in compact shared side tables rather than retaining the prototype's `AllocatableInst::operands() -> Array[Operand]` projection. Each instruction node references contiguous operand and clobber ranges; operands describe role, constraint, tie, and required timing. The shared shell owns CFG and terminator structure. Regalloc reads these tables linearly without matching target opcodes or allocating operand arrays, and produces target-independent allocation edits rather than constructing target instructions.
- 2026-07-15: Decided that register allocation does not rewrite or copy Target VCode. It returns a separate dense `Allocation` keyed by instruction and operand handles, containing physical locations, spill slots, and insertion edits. A statically typed target emitter consumes both the unchanged virtual Target VCode and its Allocation, performs constant-time location lookup, and interleaves edits at stable program points. A zero-copy allocated view may be added only for a demonstrated post-regalloc optimization need.
