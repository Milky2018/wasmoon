# ISS-368: Bring down the cost of the native sanitizer gate

## Metadata
- Type: task
- Status: closed
- Priority: 2
- Labels: ci, sanitizers, build-time, agent
- Assignee: unassigned
- Created: 2026-07-31
- Updated: 2026-08-04

## Description

The `run native sanitizer checks` step has grown until it exceeded its budget
and began failing on wall time rather than on any sanitizer finding.

Measured duration of the step on the Linux AMD64 leg:

| Date | Result | Duration |
| --- | --- | --- |
| 2026-07-28 | success | 2m20s |
| 2026-07-29 | success | 32m25s |
| 2026-07-30 02:16 | success | 33m18s |
| 2026-07-30 14:11 | failure (leak, exit 255) | 38m36s |
| 2026-07-31 09:30 | failure (timed out) | 40m13s |

The budget was raised from 40 to 75 minutes so the gate can finish and report
what it finds. That is a stopgap: the trend above is the actual problem, and the
next few files added to the gate will consume the new headroom too.

## Root cause

Almost all of the time is compilation, not test execution. The step rebuilds
every covered package with ASan/UBSan into a fresh target directory, and the
covered files sit in large packages.

From the 2026-07-31 run, measured from step start at 09:30:09:

| Elapsed | Event |
| --- | --- |
| +16m46s | first result: `wasmoon_jit/native_continuation_test.mbt`, 12 tests |
| +33m38s | second result: `wasmoon/testsuite/jit_resumable_lifecycle_test.mbt`, 2 tests |
| +33m45s | `wasmoon_jit/callback_ownership_test.mbt`, 1 test |
| +36m27s | `wasmoon/async_native/reactor_wbtest.mbt`, 8 tests |
| +38m24s | `wasmoon/wasi_component/async_preview3_wbtest.mbt`, 8 tests |
| +38m24s | `component/runtime_impl/runtime_cleanup_wbtest.mbt`, 7 tests |
| +38m24s | `component/runtime_impl/entry_state_wbtest.mbt`, 2 tests |
| killed | still compiling the next package |

Two invocations account for about 33 of the 40 minutes. The second one costs
roughly 17 minutes to compile `modules/wasmoon/testsuite` — a package of about
16k lines — in order to run two tests.

## Design

Reduce compiled volume rather than raising the budget again. Options worth
measuring, cheapest first:

1. Move the sanitizer-covered tests that live in very large packages
   (`wasmoon/testsuite`, `cmd/wasmoon/commands`) into small dedicated packages,
   so the gate compiles only what it exercises.
2. Cache or reuse the sanitizer target directory across steps or runs, if the
   sanitizer wrapper makes that sound.
3. Only if neither is workable, split the gate into independently budgeted
   steps.

Do not reduce coverage to save time: the covered files were chosen because they
exercise continuation ownership, callback ownership, reactor lifecycle, and
component teardown, which is where use-after-free and leak regressions land.

## Acceptance Criteria

- [x] The dominant compile costs are attributed per package with measurements.
- [ ] The gate completes well inside its budget without dropping covered files.
      Not met, and no longer reachable: the gate was removed.
- [x] The step budget is lowered again once the cost is reduced.

## Notes

- 2026-08-03: Applied design option 2. The build directory is now restored by
  `actions/cache@v4` and the unconditional `rm -rf` is gone, so a run rebuilds
  only what the diff touched instead of everything.

  The cache key is a digest of `moon version --all`, `clang --version`, and the
  wrapper script's contents, not of `MOONBIT_TOOLCHAIN_VERSION` — that variable
  is the literal string "nightly", so keying on it would let yesterday's
  objects survive a new compiler. `restore-keys` falls back to the newest cache
  with the same digest, so an ordinary commit restores its predecessor's
  artifacts.

  Local figures under the CI wrapper, for the `sanitizer_testsuite` closure:

  | Scenario | Time |
  | --- | ---: |
  | Clean build, nothing cached | 262s |
  | Restored cache, sources unchanged | 0.13s |

  What this does and does not buy, stated plainly: the saving is whatever the
  diff does not invalidate. A change under `.github`, `docs`, or `issues`
  rebuilds nothing and the step becomes trivial; a change to a leaf package
  rebuilds part of the closure; a change to a widely-depended package such as
  `milkir` or `logger` rebuilds most of it and saves little. A third
  measurement of that last case was taken while a benchmark occupied the
  machine, so it is not reported here — the honest claim is a large best case,
  a neutral worst case, and no change to what the gate verifies.

  Soundness is unaffected: `verify_native_sanitizers.py` inspects the produced
  binaries for sanitizer symbols and libraries after the run, so a restored
  cache cannot make an uninstrumented build report green.

  Still open until a Linux run measures the effect: the first run after this
  lands populates the cache rather than benefiting from it.

- 2026-08-04: **The 60-minute budget was wrong and is reverted to 75.** The
  first main run after the cache landed was killed by that budget —
  `The action 'run native sanitizer checks' has timed out after 60 minutes`,
  no sanitizer finding involved. Lowering 75 to 60 rested on a single 52m27s
  observation, which is not a bound on a shared runner; 12 percent of margin
  was not conservative. Lower it again only after several cached runs show a
  stable margin.

  Two things also became clear about the cache that the previous note did not
  state:

  - GitHub scopes a cache to the branch that wrote it, except that caches
    written on the default branch are readable everywhere. The cache written
    by PR #472's run was scoped to `refs/pull/472/merge` (239MB compressed)
    and was therefore invisible to main. The killed run was a cache **miss**,
    so it paid the full build plus the cache step's overhead and gained
    nothing — the worst case for this change, and the one that hit the budget.
  - The first useful measurement is the second main run, once main's own cache
    exists. That is still pending, so the value of the cache remains unproven
    on Linux.

- 2026-08-03: **Reopened.** The first Linux AMD64 run to complete this step
  after the change took **52m27s** against the new 60-minute budget
  (`run native sanitizer checks`, 10:48:07 to 11:40:34 UTC, job succeeded).
  That is inside the budget but with only about 12 percent headroom, which

  Two corrections to the reasoning that closed this issue. First, the local

  is still unmeasured — the honest statement is that the gate now completes,
  which it previously could not.

  Per-invocation attribution from that run's log, which corrects the cost
  model this issue was working from:

  | Elapsed | Invocation |
  | ---: | --- |
  | 13m06s | `moon build` of `cmd/wasmoon` (release, for the verifier) |
  | 3m45s | `wasmoon_jit` — native_continuation, 12 tests |
  | 13m28s | `sanitizer_testsuite` — jit_resumable, 2 tests |
  | 0m00s | `wasmoon_jit` reuse — callback_ownership |
  | 0m06s | `async_native` — reactor |
  | 2m37s | `wasi_component` — async_preview3 |
  | 6m45s | `component/runtime_impl` — runtime_cleanup |
  | 0m00s | `component/runtime_impl` reuse — entry_state |
  | 12m35s | `cmd/wasmoon/commands` — component_error, 17 tests |
  | 0m00s | `sanitizer_testsuite` reuse — facade, 26 tests |

  The dominant cost is **not package size**, which is what this issue and the
  move assumed. It is the dependency closure each invocation compiles for the
  first time. The new 1.1k-line `sanitizer_testsuite` still costs 13m28s on
  its first invocation because it pulls in `component`, `text_parser`, `wast`,
  `wit`, and `commands` under sanitizers; its second invocation costs 0.4s.
  Every repeat invocation against an already-compiled package is free, so the
  gate's cost is exactly the union of distinct closures plus the release
  build.

  That reframes the remaining options:

  - Three items — the release build (13m06s), the `sanitizer_testsuite`
    closure (13m28s), and the `commands` closure (12m35s) — are 75 percent of
    the step. The first two overlap heavily: `moon build cmd/wasmoon` and
    `moon test ... commands` compile much of the same tree in different
    scopes.
  - The release build exists so `verify_native_sanitizers.py` can confirm the
    shipped CLI carries the instrumentation, not just the test binaries
    (`scripts/verify_native_sanitizers.py:88-95`). Dropping it would reclaim a
    quarter of the step but weaken that check; decide deliberately rather than
    for speed.
  - Ordering is free to change and currently wastes nothing, but adding a file
    whose closure is already built is also free — that is the cheap way to
    grow coverage.

  Design option 1 is therefore spent; the next step is option 2 (reuse the
  sanitizer target directory across runs via cache, so closures are not rebuilt
  from scratch each time) or option 3 (split the gate into independently
  budgeted steps).

- 2026-07-31: Raising the budget to 75 minutes was necessary to see the gate's
  result at all. Before that, the timeout masked the outcome: the 2026-07-30
  base-branch run failed on a genuine leak at 38m36s with exit 255, while the
  following two runs were killed at the 40-minute mark, one of them 0.3 seconds
  after emitting the same leak report. A gate that cannot finish cannot be
  trusted to distinguish a real finding from a clock.
- 2026-07-31: The job-level budget went from 90 to 120 minutes to accommodate
  the step, since roughly 11 minutes of other work precedes it.

## Close Notes

Closed as obsolete rather than done: the maintainer removed the sanitizer
gate itself (see the workflow diff on `milky/remove-sanitizer-gate`), so
there is no cost left to bring down. The budget criterion above was never
met.

Two measurements are worth keeping, because they would apply again to any
future attempt at a cached native build in this repo.

**The `actions/cache` step added here never did anything.** Comparing the
last two complete Linux runs of the gate:

| | cache miss (`9753e773`) | cache hit (`abbe355e`) |
| --- | ---: | ---: |
| `moon build` | 11m57s | 12m53s |
| `sanitizer_testsuite` closure | 12m10s | 15m13s |
| `commands` closure | 10m49s | 15m23s |
| `component/runtime_impl` | 6m11s | 6m56s |
| **whole step** | **46m57s** | **57m11s** |

The hit was ten minutes *slower*, and every phase was slower by a roughly
uniform 8-40% — a slower runner, not cache behaviour. The decisive detail is
that both runs reported `ran 126 tasks` from `moon build`: identical work.
Nothing restored was reused.

**The reason is that moon's incremental build keys on source mtime, not on
content.** Verified locally, both directions:

| action | content | result |
| --- | --- | --- |
| rebuild, untouched | same | `no work to do`, 0.09s |
| `touch` every source | **identical** | 32 tasks, 13s, and the `.o`/`.c` artifacts were regenerated |
| `touch`, then restore mtimes to the recorded values | same | `no work to do`, 0.05s |

`actions/checkout` rewrites every file on every run, so every source gets an
mtime newer than anything in a restored build directory. A target-directory
cache is therefore invalid by construction on every run, whatever the key
says.

A correction to the removal's stated reason: it claimed moon supports no
route other than interception. That is wrong. ISS-323's finding covers the
CFLAGS/CXXFLAGS/LDFLAGS *environment variables*, which are ignored, but
`link.native.cc-flags` and `cc-link-flags` in a package's own config are
honoured and reach every MoonBit-generated translation unit, because the
native pipeline is whole-program. ISS-390 carries the measurements and the
replacement design.

Two fixes for the cache itself were identified and neither was pursued,
since the gate is gone:
restoring mtimes from `git log` per file (needs `fetch-depth: 0`, and would
still not help the common case here, where a change to a low-level package
invalidates every closure downstream), or content-keyed caching of the C
compilations themselves via `ccache` behind `MOON_CC` (45 of 48 compiler
invocations in a build are compiles, only 2 are links).
