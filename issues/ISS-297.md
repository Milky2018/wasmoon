# ISS-297: Parse component type indices at 64 and above

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: component-model, parser, leb128, stress, scale
- Assignee: codex
- Created: 2026-07-28
- Updated: 2026-07-28
- External ref: none

## Description
A generated component with 256 lifted functions is valid and is emitted by
wasm-tools 1.254.0, but Wasmoon rejects it with `invalid type section`.
The first failure is type index 64: `Reader::read_typeidx` incorrectly decodes
the unsigned index as signed LEB128, so the one-byte encoding `0x40` becomes
`-64`.

## Design
Decode component type indices with the shared bounded unsigned LEB128 reader.
Keep signed LEB128 only for `valtype`, where negative values encode primitive
types. Preserve explicit count and section-size limits. Keep the generated
256-function stress workload as the end-to-end regression.

## Acceptance Criteria
- [x] Component type indices 63, 64, 127, and 128 parse with unsigned
      semantics.
- [x] Truncated and overflowing count encodings still return structured parse
      errors.
- [x] The 256-function pull-request stress workload validates and invokes its
      first, last, and deeply nested exports.
- [x] Existing component snapshot suites remain unchanged.

## Close Notes

- `Reader::read_typeidx` now uses bounded unsigned LEB128; signed decoding
  remains confined to component value types.
- The 256-function smoke workload and a 4096-function local campaign both
  completed with zero failures. All pinned conformance suites still pass in
  JIT and interpreter modes.
