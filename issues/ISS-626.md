# ISS-626: Protect Core validation and Store invariants behind opaque interfaces

## Description
Core execution relies on validation and synchronized runtime metadata that its
public interfaces do not protect. Executor instantiation accepts mutable raw
`wasm_core/types.Module`; `runtime.Store` exposes mutable Array contents;
`ModuleInstance` is `pub(all)`. Parallel function/type/owner arrays and instance
address maps can be modified without their maintenance operations.

The Component path already uses abstract `ValidatedComponent` evidence and
opaque facade handles. Core needs an equally clear separation between safe
embedding operations, portable syntax models, and private runtime machinery.

## Scope and Evidence
- Review Core parsing-to-validation-to-instantiation evidence, mutation after
  validation, module/instance ownership, Store membership, callable handles,
  memory/table access, and public methods exposing metadata or parallel arrays.
- At `25381fc7`, instantiating an invalid type index through the low-level API
  aborts. [The diagnostic](../docs/evidence/runtime-quality-2026-10-14/README.md)
  explicitly records that validation rejected this input; it is not evidence of
  the CLI accepting invalid Wasm.
- Immutable field bindings containing mutable Arrays do not protect the array
  elements or correlated tables.

## Design
Provide a coherent Core embedding interface whose constructors enforce
validation and whose handles preserve ownership and invariants. Retain portable
raw models for tooling. Validation evidence must not be invalidated through
exposed mutable backing storage. Keep mutation and address resolution with the
state owner; document deliberate low-level interfaces and plan necessary
source-breaking changes for an appropriate release.

## Acceptance Criteria
- [ ] Inventory the public Core/executor/runtime interfaces and classify safe embedding operations, deliberate low-level seams, and private implementation state.
- [ ] Safe instantiation requires protected validation evidence or validates its input itself; post-validation mutation cannot silently invalidate the accepted representation.
- [ ] Public clients cannot independently mutate correlated Store/instance tables; supported operations preserve their invariants.
- [ ] Invalid, foreign-Store, closed, and stale handles receive defined behavior with targeted public-interface regressions.
- [ ] Existing host imports, shared memories, cross-module calls, GC roots, and async continuations retain their intended ownership semantics.
- [ ] Generated interfaces, compatibility/release notes, embedding examples, module dependencies, and required cross-platform checks agree with the resulting contract.
