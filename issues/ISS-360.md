# ISS-360: Reject duplicate component host readiness installation

## Metadata
- Type: bug
- Status: closed
- Priority: 2

- Assignee: codex
- Created: 2026-07-30
- Updated: 2026-07-30
- External ref: none

## Description
`WasiComponentHost` unconditionally replaces the single event loop stored in a
linker's shared `HostRuntimeState`. Installing a second WASI command host can
therefore redirect scheduler polling from the first context to the second,
while futures already created by the first host remain registered with the
first context. The second installation also overwrites linker imports.

An existing component instance can consequently lose the readiness source
required to complete its pending host operations.

## Design
Make event-loop installation a single-assignment operation on
`HostRuntimeState`, which is the shared ownership boundary used by both the
stable facade and lower-level host construction. Reject replacement before
WASI allocates resource identities or mutates linker imports. Preserve the
original event loop after rejection and map the conflict to a structured
stable-facade error.

Do not introduce per-instance polling state or silently merge unrelated WASI
contexts.

## Acceptance Criteria
- [x] Installing a second WASI command host on one component runtime is
      rejected before linker imports or readiness state are replaced.
- [x] The stable facade reports a structured duplicate-readiness error.
- [x] A pending operation owned by the first WASI context can still complete
      after the rejected installation.
- [x] A public black-box test covers two distinct WASI contexts on one runtime.
- [x] Existing Component Model, WASI, and native runtime regressions remain
      green.

## Close Notes

Closed on 2026-07-30.

- `HostRuntimeState::set_event_loop` now rejects replacement with
  `HostEventLoopAlreadyInstalled` before WASI creates resource identities or
  writes linker imports.
- The stable facade maps that conflict to
  `HostReadinessAlreadyInstalled` and closes the rejected installer context.
- Black-box tests confirm both the low-level single-assignment contract and
  that a timer registered by the first WASI context completes after a second
  installation is rejected.
- Validation passed: native tests 2501/2501; runtime-implementation tests
  33/33; WASI component tests 42/42; stable Component Model 0.2 matrix 23/23
  files and 845 commands; async 0.3 matrix 24/24 files and 153 commands.
