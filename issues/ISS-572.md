## Description
Command HTTP composition installs a synchronous native WASI reactor alongside moonbitlang/async HTTP tasks. HttpHost.drive calls progress_one_subtask_intrinsic, which can block in the native event loop while asynchronous HTTP work needs the same thread. The current types-only command guests and HTTP service suite do not exercise this mixed-I/O case.

## Acceptance Criteria
- [x] Add a command guest that waits concurrently on native WASI I/O and HTTP.
- [x] Integrate readiness without periodic polling or blocking the async scheduler.
- [ ] Verify cancellation and ownership on Linux, macOS and Windows.

## Notes
Identified during source review, not covered by the 53/55 external result. The public `async.set_external_event_loop` and `ExternalEventLoop` interfaces support host-loop integration. Adapt the native reactor to this contract rather than implementing a separate waiter thread. Related: ISS-565.

- 2026-09-28: Prerequisite dependency refresh: async 0.21.2 -> 0.22.4 and x 0.5.1 -> 0.5.5 across all workspace consumers; uri 0.1.2 remains current. Updated cancellation handling for non-error cancellation and added a component join cleanup regression. `moon info`, `moon fmt`, warning-denied native check, and all 2581 native tests pass locally. Scheduler integration remains outstanding.

- 2026-09-28: Added an `ExternalEventLoop` adapter using async's public API, context-local registration ownership over the shared native reactor, and a C-only foreign-thread wakeup callback. HTTP uses nonblocking component progress; synchronous canonical waitable waits now suspend through continuations. Async owns and joins its waiter before the adapter releases its C reference. Unix wakeup retries EINTR and does not mutate the main-thread error field.
- Regression evidence: the mixed command guest retains a 60-second native WASI timer while making a real HTTP request, then cancels the timer after receiving the response. Restoring the old blocking HTTP pump deterministically exceeds the 15-second subprocess timeout. The repaired driver passes on both engines locally.
- The standalone native/async integration executable covers native pipe readiness, timer delivery, TCP progress, cancellation, context isolation, wake-before-wait, and normal shutdown. CI runs it on Linux, macOS, and Windows; the sanitizer harness instruments and runs it separately from the ordinary native suite. Local verification passes: 2581 native tests; 36 strict C units; ASan/UBSan including the integration executable; 168 Python tests (54 platform-dependent skips); both-engine HTTP acceptance; async-0.3 (24 files, 153 commands per engine) and future-gated (12 files, 387 commands per engine). Cross-platform validation is pending.

- 2026-09-28 CI follow-up: MSVC passed the event-loop executable and both-engine mixed HTTP command. A pre-existing inheritance probe failed because it treated any valid child handle with the same numeric value as inheritance. The probe now compares connected socket endpoints and includes an inheritable socket positive control. Linux passed the integration gates but one upstream trailer-error case timed out; 20 local interpreter repetitions passed, so investigation and CI revalidation remain open.

- Follow-up regression: a shared context could drain the kernel reactor during a zero-timeout poll, stealing the wakeup intended for async's external loop. A deterministic pipe test fails before the fix and passes after enforcing a single kernel-event consumer. Shared contexts now observe persistent readiness only and reject blocking waits; ordinary synchronous CLI commands retain independent reactors. Cross-platform CI revalidation remains pending.
