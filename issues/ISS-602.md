## Description
The context still reserves a 128-byte generated-code prefix and an inline helper state for every instance. Splitting declarations into private structs does not make this allocation module-shaped. Wasmtime's 48-byte prefix is followed by module-dependent storage and does not represent all instance/Store allocations.

## Design
First establish one module layout descriptor consumed by allocation, C helpers, compiler environment paths and artifact compatibility checks. Function/memory/table/global storage must depend on actual module requirements, without a process-global layout or mutable offsets. Changing generated offsets requires an artifact revision and per-layout validation. Preserve the exported legacy layout/standalone context contract explicitly during migration.

Separately audit execution-only exception payloads, spilled locals, GC root/frame chains, scheduling and cancellation against nested entry, cross-instance bound calls, suspension and abandonment. Move state to the owning activation only after defining how standalone helper APIs work outside an active invocation. A Store-global mutable execution record is not sufficient for parked invocations.

Shared callable identities are handled by ISS-601. GC type caches and safepoint metadata need their own ownership analysis: module-local definitions, Store-specific identities and invocation roots are different kinds of state. The current safepoint owner also keeps redundant pointer arrays for data already addressed by table entries; verify removal separately from changing ABI offsets.

## Acceptance Criteria
- [ ] One layout descriptor controls native allocation and generated accesses.
- [ ] Empty/numeric, one-memory, multi-memory, table, GC and exception modules have measured total storage/allocation counts.
- [ ] Activation isolation holds for nested, suspended and cancelled invocations.
- [ ] Native and external regression suites cover both engines and artifact compatibility.
- [ ] Before/after performance does not conflate layout with allocator placement or code changes.

## Ownership review (2026-09-29)
`jit_trap_activation_push` finds the activation for the same context and detaches its exception payload, spilled locals and GC chains before reentry. Detach/attach handle suspension; abandon temporarily restores the detached state so existing context-based cleanup can release it, then restores the surviving context state. Thus these fields already have activation-scoped logical ownership but use the instance as their active storage location.

A migration must change helper access and cleanup together, retain standalone-context helper behavior, and handle bound calls into another instance plus multiple parked activations of the same instance. A single Store execution-state pointer is insufficient. No new correctness failure was established in this review, and the full migration remains open. ISS-603 removes redundant safepoint ownership arrays without changing these activation rules or generated offsets.
