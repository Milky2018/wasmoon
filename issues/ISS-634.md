# ISS-634: Invalidate native objects when shared C headers change

## Description
An incremental build during ISS-625 linked native objects compiled against two
sizes of the same private struct. Adding the pending-hostcall-exception field
in `wasmoon_jit/jit_ffi/jit_context.h` changed `jit_trap_activation_t` from 1088
to 1096 bytes on macOS ARM64. `trap.c` used the new size, while the unchanged
`native_test_support/context_test_support.c` allocated the old stack size.
Two native tests crashed. ASan independently reported a 1096-byte initialization
into the 1088-byte `outer` allocation.

Fresh native and sanitizer builds passed, with no change to those test
implementations. This establishes stale/mismatched build artifacts, but does
not yet distinguish a MoonBit transitive-header invalidation defect from missing
supported build configuration. The current toolchain is stable
`0.1.20261012 (748b63c)`.

## Scope and Evidence
- Review dependency tracking for C stubs including shared private headers across
  packages, including ordinary native, release installation and sanitizer builds.
- Preserve [the ASan observation](../docs/evidence/runtime-failures-2026-10-15/abi-cache-before.log).
- Create a small two-package header/layout change reproduction before selecting
  a tooling/configuration fix or reporting an upstream defect.

## Design
Use supported native dependency tracking or an upstream build-tool repair.
Object invalidation must follow transitive header content, not manually touched
C files or duplicated struct declarations. Clean builds remain a diagnostic
control; silently accepting incremental ABI mismatches is not the final fix.

## Acceptance Criteria
- [x] Reproduce a header-only layout change with a small fixture and identify the missing dependency or cache input.
- [ ] A normal incremental build recompiles affected native objects and executes correctly after the shared header changes.
- [ ] Ordinary native, release and sanitizer paths use consistent struct layouts; compare with clean-build controls.
- [x] Document any verified upstream limitation and the supported temporary workaround without inventing an ad hoc style audit.

## Notes
- 2026-10-16: Stable reproducer confirms 16-byte producer versus stale 8-byte consumer after a transitive shared-header edit; clean control passes. MoonBuild tracks package-local headers but does not wire compiler include discovery to n2. Enabling that mechanism additionally exposed n2 depfile escaping of paths containing spaces. Prepared isolated MoonBuild/n2 patches and failure/throughput controls are in [the investigation](../docs/evidence/native-header-dependencies-2026-10-16/README.md). Neither the installed stable toolchain nor upstream repositories were changed. Keep this issue in progress pending upstream delivery and complete platform acceptance.
- 2026-10-16: Sanitizer source copying preserved C timestamps while retaining build objects, so it was not a guaranteed fresh control. The runner now clears its own generated build directory when recreating sources; stable native 2721/2721, Python 172 (54 existing skips), and fresh macOS ASan/UBSan 163/163 with both positive controls passed. Ordinary incremental safety still requires the toolchain fix; release install already builds from a fresh private directory.
- 2026-10-16: Started a minimal two-package transitive-header reproduction on stable `0.1.20261012 (748b63c)`. Compare header-only incremental builds, mixed C/header edits and clean controls before choosing dependency tracking changes.
- 2026-10-15: During ISS-625, `moon clean --target-dir _build/native` and `moon clean --target-dir _build/sanitizers/build` removed the mismatch. The final native and sanitizer acceptance used rebuilt objects. No toolchain change was made.
