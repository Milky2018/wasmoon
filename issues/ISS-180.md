## Destination

Produce a decision-complete architecture specification and migration route in which every Wasmoon native JIT path passes from MilkIR through target-neutral MachV, then through target-specific VCode, register allocation, and emission. The map is complete when implementation can be decomposed without making further architectural decisions.

## Notes

- [`CONTEXT.md`](../CONTEXT.md) is the authoritative glossary and records the standing destination constraints established before this map was charted.
- Every session working this map must use `wayfinder`; decision sessions should also use `grilling` and `domain-modeling`, and interface-shape sessions should consult `codebase-design`.
- This map plans the architecture. It does not carry implementation into the map.
- Refer to the map and its tickets by their linked titles, not bare issue identifiers.
- The native target set is intentionally finite: AArch64 and AMD64 are required, and the design may admit one later RISC-V adapter. Do not design an open-ended runtime ISA plugin system.

## Decisions so far

<!-- Closed decision tickets are indexed here with one linked gist each. -->

- [Define the MachV semantic and legalization contract](ISS-181.md) — MachV admits fully verifiable target-neutral primitives and semantics-preserving superinstructions; target instruction and ABI forms lower later.
- [Define the MachV value and virtual-register model](ISS-182.md) — MachV uses function-owned typed SSA values, fixed 64-bit pointer/reference carriers, typed constants, and no target register or location facts.
- [Define the MachV control-flow and SSA contract](ISS-183.md) — MachV uses a function-owned rooted CFG, uniform argument-carrying edges, strict SSA, semantic program order and terminators, guarded mutation, and complete target-neutral verification.
- [Inventory current MachV coupling and migration hazards](ISS-184.md) — The current Function spans semantic IR through ABI, allocation, layout, and emission; the inventory assigns each leaked state to its future owner and records migration risks and behavior gates.
- [Prototype the generic Target VCode shell](ISS-185.md) — A generic CFG shell parameterized by closed target instruction types compiles cleanly, and target selection enters finite statically typed pipelines without a union opcode.
- [Define the MachV target-lowering interface](ISS-186.md) — Static target-owned lowering produces complete typed Target VCode with compact shared allocation and metadata tables; allocation remains separate, and no runtime target union or dynamic hot-path interface is introduced.
- [Define the ABI and call-lowering boundary](ISS-187.md) — MachV preserves logical call contracts and behavior, targets own physical call and frame planning, and Wasmoon owns only its internal cross-language contract and runtime symbol resolution.
- [Define verification at every native-code seam](ISS-188.md) — Every public stage revalidates its named ordinary-data input and output; representation-owned verifiers cover MachV, Target VCode SSA, allocation, frame layout, and unlinked code objects, while typed failures survive Wasmoon JIT orchestration.
- [Place legalization and optimization passes](ISS-189.md) — Semantic canonicalization remains target-neutral, while target-specific selection, legalization, peepholes, and frame-sensitive work belong to each static target pipeline.
- [Define Wasmoon JIT integration and artifact ownership](ISS-190.md) — Wasmoon owns the mandatory compiler, untrusted-artifact loader, versioned JIT ABI, rollback-safe installer, and persisted emitted-code format without leaking product state into reusable compiler modules.
- [Choose package and public API boundaries](ISS-191.md) — Reusable modules expose narrow semantic seams, machine targets own vertical static pipelines, and Wasmoon production compilation enters through one JIT facade with explicit breaking-version consequences.
- [Choose the migration and compatibility route](ISS-192.md) — Production cut over directly by semantic and target seams, then deleted the old representation and adapters instead of retaining compatibility modes.
- [Define architecture acceptance gates](ISS-193.md) — Dual-target correctness, verifier, metadata, artifact, interface, dependency, zero-residue, component, WASI, and sanitizer evidence closes the migration; retired backends are not performance baselines.

## Out of scope

- Implementing or migrating the compiler pipeline while this map is open.
- Turning MachV into an interpreter bytecode or adding a Pulley-style execution backend.
- Adding 32-bit host support or implementing a third native ISA in this map; a later RISC-V adapter may reuse the chosen static target seam.
- Unrelated optimizer work or backend bug fixes that do not block an architecture decision.
