# ISS-642: Enforce WAT text validity and remove quoted-malformed false positives

## Metadata

- Assignee: unassigned
- Created: 2026-10-19
- Updated: 2026-10-19

## Description
The native WAST runner historically treated every `WastModuleSource::Quote` as
malformed without parsing it (`parse_module_source`: `Quote(_) => false`). That
made malformed-text assertions appear to pass regardless of the WAT frontend's
behavior. A well-formed quoted `(module)` also satisfied `assert_malformed`.

ISS-641's portable adapter now actually parses quoted sources. The stricter
adapter and the corrected native runner expose **628 malformed-text assertions
accepted by the existing frontend across 22 Core WAST files**. The same adapter,
compiled on native and wasm, has identical results: 236/258 complete files,
61,935 passing assertions, 628 failures and zero unsupported classifications.
The previous 62,563/62,563 tally included these false positives and is superseded.

These are a family of frontend and test-contract defects, not 628 independent
interpreter execution bugs or a wasm-only regression. Keep them visible; do not
restore unconditional quoted-source rejection or classify them as unsupported.

## Reproduction
From the ISS-641 implementation workspace:

```sh
python3 scripts/run_portable_core_wast.py --output target/strict-core-wast.json
```

Minimal harness negative control:

```wast
(assert_malformed (module quote "(module)") "expected malformed text")
```

This must fail the assertion because its source is well-formed. Existing parser
counterexamples include malformed numeric tokens such as `f32.const 0e`, invalid
UTF-8 byte escapes in export names, and repeated declarations or misplaced type
annotations. Sources are in the repository's pinned `spec` corpus.

## Scope
- Lexical validity: numeric token grammar, digit separators, lane immediates,
  illegal characters, identifiers and UTF-8 string/name decoding.
- Syntactic validity: instruction/type annotation order, declaration ordering,
  duplicate names/fields/start declarations and type uses.
- Stage-correct assertions: parse malformed text rather than substituting an
  expected outcome; do not let a host capability denial satisfy an unlinkable
  assertion.
- Share assertion and source parsing contracts between native and portable WAST
  adapters; avoid future drift or a permissive fallback.

## Acceptance Criteria
- [x] Preserve the negative control proving valid quoted text cannot satisfy
  `assert_malformed` and the control separating unsupported from unlinkable.
- [x] Minimize each distinct failure family and add focused parser regressions
  plus nearby valid spellings. Fix rules, not corpus filenames or messages.
- [x] Parse/decode malformed input with strict lexical and UTF-8 checks; preserve
  stage boundaries between parsing, validation, linking and execution.
- [x] Re-run the full pinned Core corpus through native and wasm interpreter
  artifacts: all 258 files and 62,563 assertions must pass without restoring
  unconditional quote rejection, skipping inputs or changing expectations.
- [x] Pass strict MoonBit checks, shared native/wasm tests and native/JIT external
  conformance. Document the baseline false positives and final evidence clearly.

  retain bytes, including nontext data; Unicode scalar and BOM names round-trip
  without normalization. Annotation strings/comments retain lexical checks.
- 2026-10-19: Reject duplicate namespace/field/local names, imports after
  definitions, repeated starts, misplaced/repeated type uses, mismatched inline
  signatures and end/else labels, named instruction parameters, out-of-u8 SIMD
  indices and out-of-lane constants. The implicit WAST parser delegates to the
  ordinary module parser, removing its divergent duplicate implementation.
- 2026-10-19: Strict acceptance now passes 258/258 files and 62,563 assertions
  each on native interpreter, actual wasm-hosted interpreter and native JIT.
  Shared parser regressions retain valid neighbors (Unicode, BOM, arbitrary data

  assertions. The existing Component future-string fixture exposed byte-escape

  decoding must succeed before a typed Core validation rejection can pass.

- 2026-10-19: Strict corpus checking exposed premature alignment rejection.
  Binary memargs now decode bounded u32 flags (including permitted extended
  LEB encodings) and all six alignment bits; textual alignment parses an

  Reserved flags and malformed textual powers remain decoding failures.

  address width, including both import syntaxes. Address-specific bounds remain
  validator checks; table32 bounds now use unsigned comparisons for bit-63

  valid table64 bounds and genuinely malformed out-of-u64 literals.

  numeric type indices before Core validation. Named identifier resolution and
  inline signature checks retain their text-syntax rules. Both call forms now
  have native/wasm regressions for missing and high-bit indices.

- 2026-10-19: Table initializer global-scope checks moved from WAT parsing to
  Core validation. Both validator entry points restrict initializers to imported
  globals, so binary inputs receive the same protection. Regressions cover
  defined, missing, imported immutable and imported mutable globals through
  text and binary round trips, plus detailed validation diagnostics.
