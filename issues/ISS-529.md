# ISS-529: Support developer-mode Windows symlinks within directory capabilities

## Description
Verify capability-relative symlink creation with and without Windows Developer Mode under a token without the symlink privilege. Earlier assumptions that direct reparse creation always requires the privilege need runtime validation.

## Design
Keep handle-relative reparse creation. Initial CI showed creation already succeeds without the symlink privilege in Developer Mode, without entering the proposed path fallback. Remove that unnecessary fallback, verify the effective token's privilege list and use an independent raw FSCTL_SET_REPARSE_POINT control. Test renamed/replaced ancestors and concurrent parent renames through the public primitive. Preserve precise cleanup errors.

## Acceptance Criteria
- [ ] Developer Mode permits creation using a token without the symlink privilege.
- [ ] Without Developer Mode or privilege, creation fails with a permission error and leaves no placeholder.
- [ ] Concurrent ancestor/parent replacement cannot redirect creation outside the held directory.
- [ ] Existing privilege handling, relative targets, duplicates, and renamed parents retain their behavior.
- [ ] Clang/MSVC CI and full native gates pass; document tested boundaries.

## Notes
- 2026-09-15: CI 34953397831 passed the enabled/disabled Developer Mode behavior test but disproved the assumption that a path fallback is needed: its locking hook was never reached. Removed the unneeded implementation; added effective-token checks and an independent OS control before final acceptance.
- 2026-09-15: cap-primitives 3.4.5 denies FILE_SHARE_DELETE on directory opens before converting handles to paths. Wasmoon permits rename on ordinary held directories, so the fallback uses operation-scoped locks instead.
