## Description
`EGraph::merge` (`modules/milkir/egraph/egraph.mbt:739`) performs a
directed union — `union_keep(b, a)` forces the second argument to stay
root — because "many existing rewrite rules treat 'change' as
`merge(...) != class_id`". Two costs:

1. The union-find gives up union-by-rank/size, so forced directions can
   build deep parent chains that path compression then repeatedly pays
   for.
2. "Did this rule make progress?" is encoded as an implicit identity
   convention spread across dozens of rules in eight `rules_*.mbt` files.
   Any rule (or future merge change) that breaks the convention silently
   turns saturation-loop termination detection wrong in one direction or
   the other.

## Design
Make progress explicit: `merge` returns whether a union actually occurred
(or rules return their own `changed` flag), the saturation loop consumes
that signal, and the union-find regains free choice of root with
union-by-rank. Mechanical migration across the rules files; behavior
pinned by the existing rule and saturation tests plus the JIT/interp
comparison corpus.

## Acceptance Criteria
- [x] No rule determines progress by comparing merge's returned root to a
      pre-merge id.
- [x] The union-find uses rank/size-based root selection again.
- [x] Rule, saturation, and comparison suites stay green.

## Close Notes

Added `merge_changed` / `subsume_changed`, which report whether the two
classes were distinct beforehand, and migrated all 362 call sites across
16 `rules_*.mbt` files from

    let new_id = eg.merge(class_id, x)
    changed = new_id != class_id || changed

to

    changed = eg.merge_changed(class_id, x) || changed

The call stays on the left of `||` so it is never short-circuited away.
With progress explicit, `merge` no longer forces the second argument to
stay root: `UnionFind::union` returns by size (ties on the lower id, so
results stay deterministic) and `merge` derives the absorbed side from the
winner. `subsume` keeps `union_keep` — it deletes the subsumed class, so
its direction is a real requirement, not a progress convention.

A regression merges a small class into a deliberately larger one and
asserts progress is still reported although the first argument does not
survive as root — the exact case the old convention would have gotten
wrong.

Verified: egraph 196/196, milkir 175/175, wasmoon testsuite 562/562, the
full WAST corpus 258/258 files in both interpreter and JIT modes, and
`moon check --warn-list @73` clean.
