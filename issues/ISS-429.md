# ISS-429: Enforce target allocation scratch roles

## Description
The x64 and AArch64 allocation verifiers collapse distinct reserved-register
roles into one broad `is_scratch` predicate. As a result, target verification
accepts transfer-only, emitter-only, spill/edit, and fixed-operand-only
registers in allocation positions where their role forbids them. The stricter
allocator plan verifier currently catches some of these violations, but it is
optional in the Wasmoon JIT and cannot substitute for the mandatory target
allocation checkpoint.

## Design
Validate the final allocation against explicit target register roles, operand
constraints, and the kind of allocation position being checked. Value homes
admit only allocatable registers. Instruction operands admit allocatable
registers plus any reserved register named by that exact operand's `Fixed`
constraint; this preserves x64 R10's intentional dual role as an allocator
edit scratch and an atomic-operation fixed input. Allocator edits admit
allocatable registers, spill/edit scratches, and fixed-register boundary
transfers only when justified by a matching fixed operand at that program
point. Transfer and emitter scratches remain outside `Allocation` entirely.

## Acceptance Criteria
- [x] Public target allocation verification rejects transfer-only and emitter-only registers from value homes, operands, and allocation edits.
- [x] Spill/edit scratch registers are accepted in allocator edits and exactly matching fixed operands, but not unconstrained operands or value homes.
- [x] Fixed-operand-only registers are accepted only for matching fixed operands and their required boundary transfers.
- [x] Whitebox regressions cover both x64 and AArch64 role policies through `verify_allocation`.
- [x] Strict native, target, WAST, formatting, interface, and module-boundary gates pass.

## Notes
- 2026-08-13: The existing AArch64 whitebox test explicitly accepts transfer scratches through the same broad helper used for ordinary allocation operands and edits. X64 has no equivalent negative role test.
- 2026-08-14: Red tests showed both target verifiers accepted a transfer scratch as an unconstrained operand and as an allocator edit. The x64 boundary test also demonstrates why fixed-only edit validation must match the exact value, operand role, and instruction point rather than merely finding the same register on the instruction.

## Close Notes
- 2026-08-14: Replaced the broad scratch predicate with one explicit register-role mapping per target. Allocator register lists and mandatory target verification now derive permissions from those roles. X64 separately models value homes, spill/edit, fixed-only, combined spill/fixed, transfer, emitter, and reserved registers; AArch64 separately models value homes, spill/edit, transfer, stack-address, and reserved registers. The obsolete AArch64 whitebox test that asserted transfer scratches were allocation-legal was replaced by public `verify_allocation` role regressions for both targets.
- 2026-08-14: Verification passed `moon fmt`, `moon info`, native check with warning 73, `MACHV_REGALLOC_VALIDATION=1 moon test --target native --warn-list +73` (2635/2635), x64 target tests (114/114), AArch64 target tests (226/226), the module-boundary audit, core WAST in interpreter and strict JIT modes (258/258 files and 62563 assertions each), `myspec` in interpreter and strict JIT modes (13/13 files and 155 assertions each), and all three strict component JIT suites with pinned `wasm-tools` 1.254.0 (59/59 files, 1385 commands, zero skips).
