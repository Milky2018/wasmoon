# ISS-398: The register allocator's self-checks abort, next to code that raises for the same thing

## Metadata

- Status: closed

- Assignee: unassigned

## Description
Eleven `abort()` calls in `modules/regalloc` assert that the allocator's own
output is self-consistent:

| File | Sites | Claim |
| --- | --- | --- |
| `bundle_allocate.mbt` | 637, 644, 647, 650, 661, 667 | allocation left a bundle pending, lost a metric, or is not atomic |
| `bundle_plan.mbt` | 34, 43, 52, 62, 71 | the bundle plan's range/segment mapping is malformed |

The claims are correct: reaching one means the allocator is broken, not that
the input was bad. The mechanism is the problem, and the evidence is in the
same package.

`VerifyError` already exists, is already `pub`, and already has the exact
variant these want:

```moonbit
pub suberror VerifyError {
  ...
  ScratchRegisterUnavailable(message~ : String)
  InvalidPlan(message~ : String)
}
```

`verify_plan.mbt` raises `InvalidPlan` five times for this same class of
claim, and `parallel_edits.mbt:120` raises it for
`"parallel-transfer cycle has no source owner"`.

No signature needs to change. The enclosing function already declares it:

```moonbit
fn[F : FunctionView] allocate_bundle_plan(   // backtracking_allocate.mbt:1053
  ...
) -> AllocationPlan raise VerifyError {
```

`validate_bundle_allocations` and `ProductionBundlePlan::validate` are both
inside that call, and `allocate_function` already surfaces `VerifyError` to
the caller. So the same package expresses one claim two ways, and the eleven
that abort are the ones that produce SIGABRT and a message on stdout instead
of a diagnostic a caller can act on.

An allocator bug is a plausible thing to hit while developing a target. It
should report which invariant broke, not kill the process.

## Design
Convert the eleven to `raise InvalidPlan(message=...)`, keeping the existing
message text. `pick_scratch`'s exhaustion case (see ISS-399) is what
`ScratchRegisterUnavailable` was named for.

The point is not that abort is wrong for defect claims — `validated_*` in
`wasm_core` aborts deliberately and correctly (ISS-396). It is that this
package already decided to use a typed channel for exactly this class, and
these eleven predate or ignore that decision.

## Acceptance Criteria
- [x] No `abort()` remains in `modules/regalloc` for plan-consistency claims.
- [x] Each converted site raises, with its existing message kept and the
      offending id added.
- [x] Tests drive them and assert the raised error rather than the process
      dying.

## Close Notes

Eleven `abort()` calls became `raise InvalidPlan`. Six signatures needed
`raise VerifyError` threaded through -- `ProductionBundlePlan::validate`,
`build_production_bundle_plan_from_range_edges`,
`build_production_bundle_plan`, `validate_bundle_allocations`,
`allocate_bundles`, `allocate_segments_with_bundles` -- and then it met
`allocate_bundle_plan`, which already declared it. **`.mbti` is unchanged**:
every one of these is private, and the error was already on the public
signature of `allocate_function`. That is the sense in which the channel was
already there.

Messages keep their old text and gained the offending id, since a raised
error can carry what an abort could only print: `invalid production bundle
range mapping` is now `... for range 3 in bundle 1`.

The reason none of these had a test is not that they were hard to reach --
`ProductionBundlePlan` is a plain record a whitebox test can build corrupt on
purpose. It is that reaching one killed the test process. Verified by putting
a corrupt plan through the pre-change code:

```
The test executable exited with signal: 6 (SIGABRT)
Active test at executable exit:
  - iss398_probe_wbtest.mbt:2 "probe: corrupt plan under the old code"
```

Eight new whitebox tests now cover each distinct check: a plan whose declared
counts disagree with its mapping, ranges and segments claimed by the wrong
bundle, ranges and segments no bundle claims, an id past the end of the
array, and a well-formed plan raising nothing.

Verified: 2599/2599 native tests, spec corpus 258/258 files and 62563 tests in
both modes.

The three `abort()` calls in `modules/regalloc/planning` are untouched. They
are unreachable for a different reason -- nothing calls that package -- which
is ISS-399.
