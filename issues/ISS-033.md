## Description
Restoring the WASI JIT unit-test harness to production-loaded JIT code exposes a hang when a JIT-compiled function calls `wasi_snapshot_preview1.fd_write`. The same focused test used to crash with `SIGSEGV` when the direct C helper received `fd=1` as its VMContext argument. After fixing normal Wasm direct calls to pass VMContext through `CallPtr`, ordinary direct-call JIT tests pass, but the WASI import call still does not return.

## Design
Debug the import-call ABI boundary for built-in WASI imports. Confirm whether built-in WASI entries should be called through raw C helper pointers with system ABI, through Wasm-ABI hostcall import trampolines, or through dedicated adapter trampolines. Keep the final design shared by the CLI/WAST production path and testsuite; do not add a testsuite-only WASI shim as the long-term solution.

## Acceptance Criteria
- [ ] `wasi_snapshot_preview1.fd_write` called from production-loaded native JIT returns for success and EFAULT cases.
- [ ] WASI JIT tests can use production-loaded JIT code with captured stdout/stderr, stdin callbacks, and preopens.
- [ ] The production CLI/WAST JIT path and testsuite use the same import ABI setup.
- [ ] Add a focused regression test that fails on the current hang.
- [ ] `moon test --target native --warn-list +73 --diagnostic-limit=200` passes.
