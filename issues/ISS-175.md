## Description
WASIp1 defines `subscription_clock.timeout` as an unsigned 64-bit nanosecond count, but the interpreter and JIT `poll_oneoff` implementations load and compare it as signed `Int64`/`int64_t`. Values at or above `2^63` are therefore treated as negative durations. In a two-clock probe containing a relative `2^63` timeout and an immediate timeout, Wasmoon emits both events while Wasmtime emits only the immediate event.

The single-relative-clock fast path has a related failure mode: a timeout with the high bit set fails the `timeout > 0` check and completes immediately instead of representing a far-future duration.

## Design
Preserve all 64 timeout bits through decoding, ordering, remaining-duration calculation, and expiration checks. The implementation must avoid actually sleeping for impractically large durations in tests; use a mixed-subscription readiness case to verify ordering. Choose the concrete arithmetic representation after reviewing interpreter/JIT sharing and host clock limits.

## Acceptance Criteria
- [x] Relative and absolute timeout calculations preserve the full WASIp1 `u64` domain.
- [x] A far-future `2^63` timer is not reported when an immediate timer makes the same call return.
- [x] Interpreter and JIT produce the same event set at the `2^63 - 1`, `2^63`, and `u64::MAX` boundaries.
- [x] Host-duration conversion handles unrepresentable waits without signed wraparound or premature readiness.
- [x] `myspec/wasip1/poll.wast` and targeted interpreter/JIT WASI tests pass.

## Close Notes
Closed on 2026-07-15. Timeout bits remain `UInt64` from guest decoding through deadline comparison; host waits round nanoseconds up to milliseconds and cap each wait without marking the guest timer ready early. Boundary tests cover `2^63 - 1`, `2^63`, and `u64::MAX`. Verified by 9 targeted interpreter poll tests, 7 targeted JIT poll tests, `moon test --target native` (1895/1895), and `scripts/run_all_wast.py --dir myspec/wasip1 --rec` (117/117 in both interpreter and JIT modes).
