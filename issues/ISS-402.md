# ISS-402: The AArch64 branch-range fallback is not on the path the JIT compiles through

## Metadata
- Type: bug
- Status: open
- Priority: 1
- Labels: aarch64, emission, jit, robustness, agent
- Assignee: unassigned

- Updated: 2026-08-06

## Description

GitHub #486's reported failure still reproduces on current `main`. A wasm
function whose body exceeds about a megabyte of machine code fails to
compile with the same error the reporter filed:

```text
Error: JIT compilation failed: AArch64CompilationFailed(
  cause=EmissionFailed(cause=BranchOutOfRange(offset=1115408, bits=19)))
```

Reproduction, generated rather than borrowed from the reporter:

```bash
python3 scripts/gen_wide_branch_wat.py 33000 /tmp/wide33k.wat
./wasmoon run /tmp/wide33k.wat --invoke wide --arg 0
```

33,000 memory read-modify-write ops compile to roughly 1.12 MB, which puts
the enclosing `if`'s conditional branch past imm19's ±1 MB reach.

## Root cause

There are two ways to turn AArch64 VCode into machine code, and the
branch-range fallback added for #486 is on the one the JIT does not use.

| Entry point | Used by | Fallback |
| --- | --- | --- |
| `aarch64_target.emit` | `diagnose_aarch64_target`, i.e. `wasmoon explore` | yes |
| `aarch64_target.compile` | `compile_aarch64_target`, i.e. the JIT and `wasmoon run` | **no** |

`emit` wrapped `emit_verified` in a compact-then-wide retry. `compile`
called `emit_verified` directly, so a `BranchOutOfRange` from the compact
pass propagated straight out instead of being retried at the wide width.

The naming is what made this easy to get wrong: `emit_verified` reads like
"the checked, proper emit", so it is the obvious thing for a pipeline stage
to call, when it is in fact a single attempt at a fixed branch width.

The same shape has now happened three times on this issue: a fallback is
added at one site and another site bypasses it. #487 widened only the
fixups from `CodeBuffer::emit_branch` while `emit_edges.mbt` patched
directly; #490 routed those through the fixup path; this one is the entry
point above both of them.

The observable symptom was also worse than it needed to be. The compiler
computes the reason it gave up and hands it to the `Failed` stage event,
but `run` passed a no-op progress callback and logged the bare string
`JIT compilation failed`. The reporter of #486 got a detailed message
because they embed wasmoon as a library; a CLI user got nothing to act on.

## Design

Make the fallback structural rather than opt-in.

- `emit_verified` is renamed `emit_single_pass`, documented as one attempt
  at a fixed width, with the pointer to what callers actually want.
- The retry moves into `emit_with_branch_fallback`, which both `emit` and
  `compile` call. `emit` keeps the extra `verify_frame` it owes its
  callers; `compile` keeps skipping it, since `plan_frame_verified`
  already established that invariant.
- `run` forwards the `Failed` stage message, so the CLI reports the cause.

## Acceptance Criteria

- [x] The JIT's own emission path retries at the wide branch width.
- [x] A function past imm19 compiles and produces the same result as the
      interpreter.
- [x] `wasmoon run` reports why the JIT refused a module.
- [ ] A regression test drives a past-imm19 branch through `compile` at a
      cost CI can carry. Measured and rejected, see the note below.

## Notes

- 2026-08-06: What hid this is that the two entry points disagree, so the
  natural way to investigate — `wasmoon explore` — takes the path that
  works. `explore` compiled the 33,000-op module without complaint while
  `run` failed on it, which is the observation that located the seam.

- 2026-08-06: An automated regression was written and then withdrawn on
  cost. A branch only outgrows imm19 across a megabyte of code, and at four
  bytes per instruction that is upward of 262,144 instructions however the
  fixture is built — there is no way to make the span large while keeping
  the function small, because the span *is* the code size. Driving that
  through `compile` as a VCode function of chained adds, with
  `verify_allocation=false` since allocation checking dominates at that
  size (ISS-371), took the native suite from 5:10 to 16:32. Eleven minutes
  on both CI platforms for every pull request is not worth one test.

  `scripts/gen_wide_branch_wat.py` carries the reproduction instead, with
  the sizes and the expected results in its docstring. This mirrors what
  `long_branch_wbtest.mbt` already does for the encoding half: the cheap
  tests cover the mechanism, and the expensive end-to-end check is a
  documented manual procedure.
