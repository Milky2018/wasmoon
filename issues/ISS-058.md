# ISS-058: Make MachV Function the production machine IR

## Description
The native JIT production path still lowers MilkIR into
`@machv_regalloc.VCodeFunction`, then emits from that data model. This means
`machv_regalloc` still owns the effective production machine IR even though the
architecture target is for MachV to be the reusable virtual-register machine IR.

Evidence:
- `modules/isa_target/lower/pkg.generated.mbti` exposes `lower_function(...)-> @machv_regalloc.VCodeFunction`.
- `modules/wasmoon_jit/native_glue.mbt` plans and emits from `@machv_regalloc.VCodeFunction`.
- `modules/machv_emit/pkg.generated.mbti` exposes emitter APIs over `@machv_regalloc.VCodeFunction`.

## Design
Move the production lowering, register-allocation adapter, and emitter boundary
to `@machv.Function`. `machv_regalloc` should become a projection and
materialization layer for MachV functions, not the owner of a duplicate
machine-function representation. Preserve the current generated code behavior
by mechanically migrating fields and operations from the existing production
path instead of hand-writing substitute logic.

Non-goal: redesign the instruction selector or allocator policy while changing
the data model boundary.

## Acceptance Criteria
- [x] `isa_target/lower` production APIs return `@machv.Function` or a target-owned wrapper over `@machv.Function`, not `@machv_regalloc.VCodeFunction`.
- [x] `wasmoon_jit` no longer passes `@machv_regalloc.VCodeFunction` through the production native JIT path.
- [x] `machv_emit` production APIs emit from `@machv.Function` plus generic allocation metadata.
- [x] `machv_regalloc.VCodeFunction` is removed, made private test-only, or reduced to a temporary compatibility adapter that is not used by production Wasmoon JIT.
- [x] Existing behavior is preserved by copying and mechanically moving the old production logic where possible.
- [x] `moon info --target native` is run and generated `.mbti` diffs are reviewed.

## Notes
- 2026-07-06: Created from the abstraction-leak audit after ISS-057. This is the highest-priority leak because it makes MachV non-authoritative in the real production path.
- 2026-07-06: Started implementation. The intended first slice is to make
  `@machv.Function` own the existing production VCode-shaped machine function
  API, then retarget lowering, regalloc, emission, and JIT planning to that
  type without changing allocator or emitter semantics.

## Close Notes
Closed on 2026-07-06 by making `@machv.Function` own the existing production
VCode-shaped machine function model. The old root MachV prototype function was
renamed to `@machv.AbstractFunction` for the older x64/AArch64 target and
linear-scan tests, while the production lowering, backtracking regalloc,
layout, emitter, JIT glue, and Wasmoon assembly path now use `@machv.Function`
directly. `modules/machv_regalloc/function.mbt` was removed, and generated
interfaces no longer expose `VCodeFunction`.

The migration also replaced the former MilkIR return-type payload on the
production machine function with `@machv.ValueKind`, so this step does not move
the `@milkir.Type` dependency into MachV.
