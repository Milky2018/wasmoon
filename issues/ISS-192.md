## Question

In what verified order can the current union-style MachV pipeline be replaced while keeping AArch64 and AMD64 behavior observable, avoiding a long-lived dual semantic source of truth, and respecting downstream API compatibility constraints?

## Acceptance Criteria

- [ ] The route is divided into behavior-preserving milestones with explicit rollback or comparison points.
- [ ] Temporary adapters have deletion conditions and cannot become permanent compatibility APIs.
- [ ] Current consumers, public APIs, generated interfaces, Cwasm behavior, and native tests have a migration treatment.

## Notes
- 2026-07-15: Implementation slicing begins only after this map closes; this ticket decides the route rather than executing it.
- 2026-07-16: Claimed for a HITL migration-design session using Markdown issue tracking, deep-module seam analysis, and one-decision-at-a-time grilling. The route will prefer behavior-preserving replacement milestones over a long-lived layered backend, give every temporary adapter an explicit deletion condition, and make no production migration changes while this ticket remains open.
- 2026-07-16: Decided on a semantic-front-first replacement route. The first implementation establishes the target-neutral MachV producer and verifier, then uses one private temporary semantic-MachV-to-legacy-MachV adapter so the existing register allocator and emitters remain usable. During a bounded test-only comparison window, the current MilkIR-to-union path and the new semantic path are both run and compared. Once parity gates pass, production switches to semantic MachV through the adapter and the old MilkIR-to-union lowering is deleted immediately, restoring one semantic source of truth before Target VCode migration continues.
- 2026-07-16: The private legacy adapter is a migration seam, not a supported compatibility interface. Its implementation should mechanically reuse known-good legacy lowering wherever possible rather than independently reimplementing equivalent target behavior. AArch64 and AMD64 are then replaced behind the target seam by their own Target VCode pipelines; after both targets no longer consume legacy MachV, the adapter, shared target-opcode union, legacy allocation representation, and shared emitter are deleted.
- 2026-07-16: Rejected emitter-first and big-bang routes. Emitter-first would force the new backend to consume an already target- and ABI-shaped legacy representation, while a big-bang replacement would remove useful comparison and rollback points. Each accepted migration milestone must be independently revertible to the preceding verified commit.
- 2026-07-16: Decided to migrate complete vertical targets rather than operation families across both targets. AArch64 is the first tracer bullet: its MachV-to-AArch64-VCode lowering, allocation adapter, frame planning, emitter, verifier checkpoints, and parity gates are completed and cut over as one target pipeline while AMD64 continues through the private legacy adapter. AMD64 is then migrated through the same established seams. Only after both vertical pipelines are live may the adapter and union backend be deleted.
- 2026-07-16: AArch64 is first because the current shared opcode, SIMD, addressing, and emission implementation already encode many AArch64-shaped assumptions, so the initial migration can preserve behavior through mechanical relocation. AMD64 second is an intentional architecture test: it must fit the generic MachV and Target VCode seams without adding AArch64 compatibility concepts or reopening a shared target union.
- 2026-07-16: Decided that shadow compilation is available only to tests and diagnostics. Production CLI, runtime, and JIT requests execute exactly one selected backend and never compile through both paths. Comparison gates may inspect structured stage output, relocations and fixups, trap and GC safepoint metadata, normalized disassembly, and executed JIT behavior, but byte-for-byte machine-code equality is not required because legal allocation, layout, selection, and constant-pool choices may differ. The Cwasm wire schema remains compatible while newly produced bytes and offsets may change.
- 2026-07-16: Target cutover uses no long-lived runtime feature flag and no automatic fallback to the legacy backend. A new-backend failure is a structured compilation failure so coverage gaps cannot be hidden. Rollback means reverting the complete verified cutover commit or milestone, not silently recompiling with legacy code. Any dual-backend diagnostic entry remains internal and is deleted with the comparison window rather than becoming a supported library interface.
- 2026-07-16: Decided that the temporary legacy adapter lives only inside the implementation of the old target-aware `milkir_machv/lower` migration source. It accepts verified semantic MachV and mechanically reuses or relocates the known-good legacy target lowering needed to produce union MachV. It is absent from generated interfaces, the semantic `machv` module, Wasmoon JIT, and supported target interfaces; only legacy lowering internals and the test-only comparison harness may call it. No shared public target union interface is introduced for the adapter.
- 2026-07-16: The adapter has staged deletion conditions. Deleting the old MilkIR-to-union entry is part of the semantic MachV production cutover; deleting the AArch64 adapter branch is part of AArch64 Target VCode cutover; and deleting the remaining adapter implementation, target-aware `milkir_machv/lower` surface, and comparison entry is part of AMD64 cutover. Boundary checks must prevent reusable or public packages from importing or re-exporting the adapter. A missed deletion condition fails that milestone rather than creating a compatibility extension.
- 2026-07-16: Decided on a direct generational break rather than downstream source compatibility. The migration does not preserve old constructors, types, package paths, forwarding methods, deprecated aliases, compatibility wrappers, or a supported coexistence period. Repository consumers move to the new interfaces as part of the cutover, and the final tree contains only the new architecture. Previously published versions and external consumers pinned to them are not migration acceptance constraints.
- 2026-07-16: Release numbering still communicates breaking interfaces according to the repository's pre-1.0 convention, but versioned compatibility is not used as an architectural seam. Retired modules such as `machv_emit` and `wasm_isa_lower` are removed from the new dependency graph rather than receiving compatibility releases. Generated interface review checks that legacy surfaces and migration adapters are absent, not that old downstream source continues to compile.
- 2026-07-16: Decided that every implementation milestone leaves the repository buildable, testable, and independently revertible even though no old public interface compatibility is promised. Private migration adapters may preserve internal compilation continuity, while one milestone may atomically remove a legacy interface and migrate every repository caller. Intermediate commits are not published. A representation change that cannot be safely split may use one larger atomic commit, but the commit boundary must restore the applicable verification gates; a long-lived uncompilable rewrite period is not an accepted migration technique.
