## Question

Which value kinds, pointer/reference carriers, virtual-register classes, constants, abstract locations, and signature facts belong in MachV without importing physical-register banks or target ABI policy?

## Design

MachV uses function-owned, single-definition SSA values with the exact type set `I32`, `I64`, `F32`, `F64`, `V128`, `Ptr64`, and `GcRef64`. A value is an opaque dense handle scoped by a private function owner; its function owns the canonical value-type table and rejects foreign values before mutation. `Ptr64` and nullable, GC-tracked `GcRef64` are fixed 64-bit carriers. Narrow integers exist only as memory access widths, and comparisons produce `I32`.

Constants are typed SSA-producing operations with bit-exact payloads, distinct null pointer and managed-reference forms, and symbolic external addresses. MachV has no register classes, physical or fixed registers, allocated locations, spill or ABI slots, stack-pointer mechanics, frame layout, calling conventions, clobber sets, or target immediate and constant-pool policy.

A MachV function signature contains only ordered parameter and result value types. Function parameters are its initial SSA values, including an explicit `Ptr64` hidden context when needed. Returns, ordinary calls, and tail calls must match these types exactly. Effects, safepoints, unwind behavior, ABI placement, extension attributes, and prologue or epilogue policy are separate downstream contracts.

- 2026-07-15: Every MachV function parameter, block parameter, and instruction result carries an exact target-neutral value type. Register classes are not MachV value types; each target maps MachV types to its own Target VCode register classes after MachV lowering.
- 2026-07-15: A MachV function owns one canonical dense table from opaque value handles to MachV value types. Instructions and parameter lists carry only handles; builders allocate them, and verification, printing, and lowering query the same function-owned facts. Public `{ id, type }` construction and duplicated per-use type fields are excluded.
- 2026-07-15: Opaque value handles internally combine a dense id with a private per-function owner context. Low-level mutation rejects foreign values before changing the function and records a construction error. Clone, rebuild, and deserialization allocate a fresh owner context and remap handles; owner identity is absent from printed and serialized forms.
- 2026-07-15: The complete MachV value-type set is `I32`, `I64`, `F32`, `F64`, `V128`, `Ptr64`, and `GcRef64`. Narrow integers are memory widths rather than values, and comparisons produce `I32`. `Ptr64` is an untraced address or opaque handle; `GcRef64` is a nullable managed root. Both are fixed 64-bit carriers. Source-level callable and opaque reference distinctions are removed during semantic legalization, while call operations validate callee meaning independently.
- 2026-07-15: Constants are typed SSA-producing semantic operations. Integer, floating-point, and `V128` payloads preserve exact bits; null pointer and null managed-reference constants remain distinct. External code or data addresses use symbolic address constants resolved by relocation. Nonzero process addresses, target immediate variants, constant-pool layout, and pooling policy are excluded from MachV.
- 2026-07-15: MachV has no value-location vocabulary. Physical and fixed registers, spill and callee-saved slots, incoming or outgoing ABI areas, return areas, stack-pointer operations, and frame layout begin in Target VCode, register allocation, or frame layout. Safepoints identify live `GcRef64` values rather than stack offsets. A future address-visible semantic stack object requires a separate decision and is not added without a producer.
- 2026-07-15: A MachV function signature contains only ordered parameter and result value types. Function parameters are initial SSA values, including an explicit `Ptr64` hidden context when present. Return, ordinary call, and tail-call values match the signature exactly. Register classes, locations, stack counts, extension attributes, calling conventions, effects, safepoints, and unwind summaries are not signature facts.
