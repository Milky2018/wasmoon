## Question

Which transformations belong before MachV, in target-neutral MachV, during target lowering, or on target-specific VCode, and how do we prevent target peepholes from leaking target instruction forms back into MachV?

## Acceptance Criteria

- [x] Semantic optimization, target-neutral legalization, instruction selection, target peepholes, and post-allocation cleanup have distinct owners.
- [x] Target-side fusion rules are stated for representative shifted, extended, remainder, compare, call, and vector cases.
- [x] Pass placement preserves correctness and does not require a shared target-opcode union.

## Notes
- 2026-07-15: Pulley superinstructions are motivated by interpreter dispatch; MachV needs an independent pass-placement rationale.
- 2026-07-16: Claimed for a HITL architecture decision session using the established one-ticket discipline with domain modeling, deep-module pass ownership analysis, grilling, and Markdown issue tracking. Current passes are evidence rather than destination constraints, and no production implementation will occur while this ticket is open.
- 2026-07-16: Decided on six distinct transformation layers. MilkIR owns high-level semantic optimization; `milkir_machv` owns mandatory target-neutral semantic legalization; MachV owns only a small target-neutral late-cleanup pipeline; each machine target owns instruction selection, target legalization, and pre-allocation Target VCode peepholes and block layout; `machv_regalloc` owns allocation and insertion edits without inspecting target instructions; and each machine target owns constrained post-allocation cleanup, frame planning, branch relaxation, constant pools, veneers, and emission.
- 2026-07-16: The MachV late-cleanup layer is deliberately not a second middle end. A pass may enter it only when it neither queries nor encodes an ISA, ABI, physical register, immediate range, addressing mode, or target cost, and when it either removes artifacts introduced by semantic lowering or has demonstrated target-independent benefit for every supported native target. Otherwise the transform remains in MilkIR or moves to the owning machine target.
- 2026-07-16: Target VCode block layout must be selected before register allocation so instruction handles and program points remain stable throughout allocation. Emission may perform only size-dependent branch relaxation and physical code layout such as veneers and constant pools; it does not own semantic CFG optimization. Regalloc consumes compact target-provided operand, constraint, clobber, and rematerialization facts and returns allocation locations and insertion edits without matching target opcodes.
- 2026-07-16: Decided that MachV retains independent semantic shifts, extensions, arithmetic, and memory accesses and never adds shifted operands, extended operands, LEA forms, or target addressing modes. MachV late cleanup may remove only target-neutral identities and redundancies such as zero shifts, equal-width extensions, and redundant extend or truncate chains.
- 2026-07-16: AArch64 and AMD64 target lowering statically recognize the same MachV expression graph and independently select their encodable forms: for example, AArch64 may select a shifted or extended operand while AMD64 may select LEA or a base-index-scale-displacement address. Immediate ranges, shift limits, scales, register classes, and addressing legality are target facts. Fusion normally occurs during whole-function target lowering; a pre-allocation Target VCode peephole is reserved for local opportunities exposed only after target legalization.
- 2026-07-16: Target fusion may subsume a producer only when its value has no remaining use. A target may duplicate a demonstrably cheap computation for a profitable multi-use pattern under its own cost policy, but it must preserve the original definition for other uses. Target patterns are direct typed code over the owning MachV and Target VCode types, not string-named rewrite tables, a shared pattern DSL, or target-shaped MachV opcodes.
- 2026-07-16: Decided that MachV retains semantic signed and unsigned remainder operations with explicit widths rather than expanding them into target-shaped arithmetic. Signed remainder traps only on a zero divisor and returns zero for `INT_MIN % -1`. AArch64 target lowering may select division followed by multiply-subtract; AMD64 target lowering owns the fixed dividend, quotient, and remainder register constraints and must bypass the hardware `IDIV` overflow for the `INT_MIN % -1` case. The complete sequence and trap control flow exist in Target VCode rather than being hidden inside emission.
- 2026-07-16: Constant-divisor strength reduction and reuse of one division for compatible quotient and remainder computations are target-owned profitability decisions. Reuse is legal only when execution conditions, trap order, effects, safepoints, and metadata remain equivalent; the initial implementation may require adjacent operations with no intervening observable operation.
- 2026-07-16: Decided that every MachV integer or floating comparison produces an ordinary target-neutral SSA boolean and MachV never models machine flags. Target lowering may consume a single-use comparison directly into a target branch or select, use target zero, bit-test, immediate, or condition forms, or materialize the boolean with the target's set-on-condition sequence. Multi-use comparisons may be repeated or materialized according to target cost while preserving all uses. Fused compare-branch and compare-select forms belong only to the owning Target VCode; they do not expose flags SSA or an implicit adjacency contract in the shared shell.
- 2026-07-16: Decided that MachV calls retain only the target-neutral callee, logical signature, explicit arguments and results, protocol, and canonical effects, traps, unwind, and safepoint facts. Target lowering owns direct versus indirect call selection, ABI argument and result locations, outgoing stack objects, fixed operands, and clobbers. A single-use symbolic address may be subsumed by call selection, but conditional calls remain explicit MachV control flow and ordinary calls are never implicitly converted into tail calls. Only a semantic MachV `TailCall` terminator enters target tail-call lowering, which must prove the ABI contract or return a structured error.
- 2026-07-16: Decided that MachV retains parameterized semantic `V128` operations, including fused operations only when decomposition would change rounding, saturation, lane layout, or another observable semantic property. Each target owns SIMD feature selection, instruction fusion, and legalization. Load-splat, load-extend, and load-lane fusion require a single-use load, an exactly matching access, one physical memory access, and preserved trap, effect, source, and safepoint order. Pure vector expression fusion is target-owned, but it cannot infer a stronger floating-point or relaxed semantic contract than MachV provides.
- 2026-07-16: Unsupported vector operations lower into an explicit complete Target VCode sequence. Every temporary is a real Target VCode virtual value visible to register allocation; target emitters may not hide multi-instruction expansion or undocumented scratch-register requirements behind one opcode. Vector constants may select a target immediate or a symbolic constant-pool reference, while final pool placement and displacement resolution remain emission concerns.
- 2026-07-16: Decided that the product exposes one optimization level rather than individual pass switches. O0 still performs every correctness legalization, verifier checkpoint, direct instruction selection, and cheap mandatory cleanup; O1 adds inexpensive semantic and target-local optimization; O2 adds the normal budgeted MilkIR and target pipelines; and O3 adds expensive semantic optimization such as loop transforms. A target may initially map O3 to its O2 policy until measurement justifies an additional target pass. O0 must not deliberately avoid an obvious constant-time instruction selection.
- 2026-07-16: The mandatory pipeline is MilkIR cleanup and verification, semantic MilkIR-to-MachV legalization, small target-neutral MachV cleanup, MachV verification, target instruction selection plus ABI and target legalization, Target VCode verification, target-owned block layout, register allocation and Allocation verification, constrained target post-allocation cleanup, frame planning and verification, and emission. Optional target peepholes run before block layout. Mandatory work is never disabled by function-size thresholds; expensive work uses explicit budgets, safe partial results, and early termination.
- 2026-07-16: Post-allocation cleanup operates only on the target-owned Allocation and insertion-edit plan while Target VCode, block order, instruction handles, and program points remain unchanged. It may remove same-location moves, combine barrier-free adjacent edits, eliminate proven redundant reloads, normalize spill or reload edits, and select an equivalent physical encoding. It may not change CFG, defs, uses, constraints, clobbers, calls, traps, safepoints, GC roots, metadata, or temporary-register requirements. Any transform that requires new liveness must run before allocation or explicitly rerun allocation; emission owns no semantic instruction-deleting peephole.

Shifted and extended operands, remainder, compare, call, and vector cases are classified without introducing a target opcode union.
