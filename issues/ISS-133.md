# ISS-133: Establish a semantic MilkIR opcode hierarchy

## Description
MilkIR currently places generic scalar SSA operations, raw pointer and call operations, Wasm-shaped SIMD operations, source-level memory immediates, dialect extensions, untyped custom operations, and unsupported legacy operations in one flat opcode enum. Several fields participate in printing and instruction identity even though lowering ignores them, while some operations pass verification but are rejected by every production lowering path.

## Design
Make MilkIR a post-source-semantics, pre-target IR. Organize supported core semantics into scalar, memory, call, vector, and extension families; consume Wasm module information in the Wasm frontend or dialect adapter; distinguish dialect-bearing functions from functions accepted by generic lowering; and delete compatibility forms after all producers and consumers migrate. Use expand-contract slices so each intermediate state remains testable.

## Acceptance Criteria
- [x] Core opcodes have complete verifier, effect/trap, printer, optimizer, and lowering contracts.
- [x] Valid generic core IR contains no unconsumed Wasm module information.
- [x] Generic lowering does not silently accept dialect operations or unsupported compatibility opcodes.
- [x] Opcode families expose semantic groupings instead of one flat source-language-shaped enum.
- [x] Native, wasm-gc, JIT/interpreter, and module-boundary gates remain green.
