# ISS-394: Two CLI binaries declare their own `exit` FFI around a stale warning

## Description
Both CLI binaries declared their own extern:

```moonbit
/// Native exit function with correct void return type
/// (moonbitlang/x/sys declares exit as returning int32, which causes a warning)
extern "c" fn native_exit(code : Int) = "exit"
```

once in `cmd/wasmoon/commands/run.mbt` and once in `cmd/wasmoon-tools/main.mbt`.
`cmd/wasmoon` then used both seams: `native_exit` in the command
implementations and `@sys.exit` in `main.mbt`.

The comment's premise no longer holds. `moonbitlang/x` 0.4.38 declares

```moonbit
pub extern "C" fn exit(code : Int) -> Unit = "exit"
```

returning `Unit`, so there is no warning to work around and nothing the local
declaration buys. Both resolve to the same C `exit`, so this was duplication
rather than a behavioural difference.

## Acceptance Criteria
- [x] No package declares its own `exit` extern.

- [x] Every exit code both binaries produce is unchanged, checked by running

## Close Notes

Both externs are gone; `exit_failure` and `exit_error` call `@sys.exit`, and
`moonbitlang/x/sys` is now imported by `cmd/wasmoon-tools` as well.

The comment's claim was tested rather than taken on trust: `moon check
--target native --warn-list @73` is clean afterwards, which is the exact
invocation CI uses and the one that would have surfaced the warning.

Behaviour was checked by running both binaries, not by reading the diff.
`scripts/cli_behavior_test.py` covers `wasmoon` — 14 checks, all passing —
and `wasmoon-tools` was exercised by hand, since nothing automated covers it:

| `validate` on a valid module | 0 |
| `validate` on a missing file | 1, stdout empty |
