## Description

`machv_regalloc` still flattens every VCode function into an owned
`VCodeFunctionView`, asks generic regalloc to build an `AllocationPlan`, and
then walks all values, operands, edits, spill slots, and GC roots again to build
target `Allocation` tables. AEGIS-128L spends about 1,055 us constructing the
view and 3,393 us translating the plan, in addition to allocator work.

## Design

Make VCode satisfy the allocator's read interface through non-owning indexed
access and let an injected allocation sink receive dense value, operand, edit,
spill-slot, and safepoint results in target table shape. Standalone regalloc
tests use an in-memory sink adapter. Production uses the VCode allocation-table
adapter. Keep allocation policy and target-independent tests inside `regalloc`.

Do not merge target instruction semantics into generic regalloc, weaken strict
validation, or retain the old copy path as a second production implementation.

## Acceptance Criteria
- [ ] Production regalloc does not construct owned copies of VCode layout, operands, clobbers, successors, or edge arguments.
- [ ] Production regalloc does not materialize a generic `AllocationPlan` and then translate every result into another allocation object.
- [ ] The generic allocator remains target-independent and is testable through one non-owning function interface and one result-sink interface.
- [ ] Allocation decisions, spills, reloads, moves, scratch roles, safepoint roots, frame layout, and generated code remain unchanged.
- [ ] Seven cache-isolated AEGIS-128L runs remove the measured view and plan-translation costs and improve complete regalloc materially.
- [ ] Normal and `MACHV_REGALLOC_VALIDATION=1` native tests, both targets, formatting, warning-73, generated interfaces, and module boundaries pass.
