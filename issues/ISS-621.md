# ISS-621: Encode component value type indices with signed LEB

## Description
While adding a type-depth boundary regression for ISS-620, a valid chain of 100 list types emitted by parse_component_wat failed parse_component with InvalidTypeSection before validation. In modules/wasm_component/text/component_wat.mbt, push_valtype_encoding writes TypeIdx with push_uleb_u32, while model/type_section.mbt::parse_valtype reads signed LEB. Index 64 is encoded as 0x40, which the reader interprets as -64, not a valid primitive type. Indices 0 through 63 conceal the error. The canonical-value encoder already uses push_sleb_i32.

## Design
Use the component value-type signed encoding for type references. Review other value-type emission paths for the same mistake without changing index spaces that require unsigned encoding.

## Acceptance Criteria
- [x] Reproduce text-to-binary parsing failures at affected indices, including 64.
- [x] Encode value-type references correctly and round-trip representative indices 63, 64, 127 and 128 with exact parsed type-index assertions.
- [x] Validate the 100-deep list chain and reject the 101-deep chain for the depth limit rather than binary parse failure.
- [x] Run component text/model/validator regressions and relevant repository checks.

## Close Notes
Fixed locally on 2026-10-12 after PR #530 merged as 09203bc2. The shared
push_valtype_encoding helper now uses push_sleb_i32 for TypeIdx, matching the
model reader and existing canonical value-type encoder. Reviewed the other
TypeIdx encoder and own/borrow, type-bound, function/type-reference and resource
destructor index writes: those separate unsigned index fields remain unchanged.

The new round-trip regression compares exact parsed List(TypeIdx(index)) values
and validates the components at indices 63, 64, 127 and 128. Before the fix its
results were true/false/false/true; after the fix all four pass. This covers both
parse rejection and an index being decoded as a different value type. The depth
boundary regression now starts from component text, accepts depth 100 and rejects
101 during validation, replacing the direct-binary workaround from ISS-620.

Validation: text package 14/14; full `moon test --target native` 2,639/2,639;
`moon info`, `moon fmt`, `moon check --target native --warn-list +73 --deny-warn`
and `git diff --check` passed. No public interface changes. These results are
local macOS ARM64 checks; no remote CI run is claimed for this fix.
