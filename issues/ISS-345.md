# ISS-345: Split component task progress from host readiness waiting

## Description
The current scheduler progress helper may call the host event loop's blocking
wait operation. It therefore cannot implement a truthful nonblocking
`ComponentCall::poll`, and the stable interface has no MoonBit async join path.

## Design
Separate bounded nonblocking task progress, blocking native readiness waiting,
and MoonBit process suspension. Keep the component scheduler authoritative for
guest tasks and use the host reactor only for I/O readiness; do not introduce a
second component task scheduler.

## Acceptance Criteria
- [x] Nonblocking scheduler progress never invokes a blocking reactor wait.
- [x] Blocking wait uses kqueue/epoll only when no guest task can progress.
- [x] Async join suspends the MoonBit process without creating an OS thread.
- [x] Fairness, deadlock, cancellation, and no-replay contracts remain intact.
- [x] Black-box tests show another MoonBit process progresses while a component call is pending.

## Close Notes

Separated bounded guest progress, zero-timeout host-event polling, and blocking
host readiness waiting. `ComponentCall::join` uses `moonbitlang/async` process
suspension while retaining the same component task and continuation; it does
not create an OS thread or a second guest scheduler. Black-box async tests prove
that another MoonBit process runs while the component call is pending.
