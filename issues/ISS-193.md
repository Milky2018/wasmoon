## Question

Which compile-time, verification, differential-correctness, code-quality, code-size, compile-time, and runtime-performance gates must the completed migration satisfy before the old MachV representation can be removed?

## Acceptance Criteria

- [ ] Required unit, snapshot, verifier-negative, JIT/interpreter differential, WAST, component, and WASI gates are named.
- [ ] AArch64 and AMD64 correctness and performance comparison baselines are specified.
- [ ] Boundary audits and API/interface checks are included alongside runtime tests.

## Notes
- 2026-07-15: CI availability is not itself the architecture; the resolution must distinguish required evidence from temporarily unavailable runners.
- 2026-07-16: Claimed to define executable correctness, interface, artifact, code-quality, compile-time, code-size, and runtime-performance gates before ISS-194 may begin. Repository facts will be measured first; only policy thresholds and tradeoffs require HITL decisions.
- 2026-07-16: Current correctness CI runs `moon check`, all MoonBit native tests with `MACHV_REGALLOC_VALIDATION=1`, formatting/interface drift checks, release builds, component WAST, and core WAST on both `macos-latest` and `ubuntu-latest`. Ubuntu additionally runs ASan/UBSan GC differential stress. The jobs do not assert the actual host architecture, so the final AArch64/AMD64 gates must record and reject an unexpected `uname -m`.
- 2026-07-16: The Preview 1 CLI integration suite at `examples/wasi_tests/wasi_test.py` exercises 43 cases through both JIT and interpreter, but it is not currently invoked by GitHub Actions. It must become an explicit target-cutover gate rather than being inferred from `moon test`.
- 2026-07-16: Current performance CI is scheduled Ubuntu-only and warning-only. It uses 15% elapsed, 15% compile-time, and 5% code-size thresholds plus Wasmtime ratios, but neither `docs/perf/baselines/linux-amd64/perf-summary.json` nor `docs/perf/baselines/darwin-arm64/perf-summary.json` exists in the current tree.
- 2026-07-16: The existing benchmark runner cannot currently establish a complete baseline: on local Apple Silicon, three of its four default run workloads (`core3`, `stream`, and `box_easy2`) fail JIT compilation before metrics are written. The surviving `benchmark.wasm` probe over seven measured runs showed wall-time CV about 2.08%, compile-time CV about 5.88%, and deterministic 680-byte code size. A migration gate therefore needs repaired workloads and paired same-runner comparison rather than a single absolute historical timing.
- 2026-07-16: Existing opt-in metrics already expose module and per-function compile time, optimize/lower/regalloc/emit phases, code size, spills, reloads, moves, and pass work. The missing infrastructure is a legacy/new paired runner, stable aggregation and variance handling, target identity, and hard-failure integration for cutover milestones.
- 2026-07-16: Decided that performance regressions are target-cutover blockers, not warning-only nightly findings. Cutover evidence must use paired legacy/new measurements on the same runner. Correctness, verifier, and artifact-metadata mismatches have zero tolerance; deterministic code-size and statistically evaluated compile/runtime regressions use explicit hard thresholds. A failed gate stops the cutover without production fallback. Accepting a known regression requires an explicitly approved follow-up ISS, and the affected legacy path cannot be deleted until that issue is closed.
- 2026-07-16: Decided on two comparison baselines with only one blocking authority. Before ISS-194 begins, record one fixed legacy Git commit, toolchain identity, target identity, and workload manifest for each of AArch64 and AMD64. Every target cutover rebuilds that fixed commit and the candidate on the same runner and measures them as paired samples; the candidate's parent commit is an additional diagnostic baseline only. Machine-specific absolute timings are not committed as performance truth. After source deletion, CI continues to build the fixed Git commit in a separate worktree, so performance comparison does not justify retaining `machv_legacy` in the candidate tree.
- 2026-07-16: Approved strict two-level performance budgets. Runtime geometric-mean regression across the workload corpus is at most 3%, with no individual workload above 5%. JIT compile-time geometric-mean regression is at most 5%, with no individual workload above 10%. Total emitted code bytes across the corpus may not increase, and no individual workload may increase by more than 5%. Spill, reload, move, and per-phase metrics are mandatory diagnostics but are not independent blockers.
- 2026-07-16: Paired comparison uses one warmup followed by nine alternating-order legacy/candidate pairs. If observed noise exceeds half of the applicable budget, expand to twenty-one pairs. A result that remains statistically inconclusive blocks cutover. Workloads dominated by process startup must repeat execution inside the module rather than receive a relaxed threshold.
- 2026-07-16: Decided that repository-owned tests, verifiers, snapshots, artifact round trips, and WASI integration tests must pass absolutely. A confirmed external MoonBit-nightly, WAST-tooling, or component-tooling failure may be represented only by an exact expected-failure manifest entry containing the test path, target, toolchain version, failure fingerprint, and tracking ISS. The fixed legacy baseline and candidate must reproduce the same failure on the same toolchain; any new failure or changed failure mode blocks cutover.
- 2026-07-16: Directory-level exclusions, broad regular expressions, `|| true`, and untracked skip lists cannot satisfy a gate. An expected failure that unexpectedly passes also fails CI until the obsolete manifest entry is removed, preventing external-toolchain exceptions from becoming permanent coverage holes.
- 2026-07-16: Approved the formal target-cutover correctness matrix on real target hardware: `moon check --target native`; all native MoonBit tests with `MACHV_REGALLOC_VALIDATION=1`; full core WAST in JIT and interpreter modes with explicit JIT-only regression reporting; full component-spec; all 43 Preview 1 CLI cases in both JIT and interpreter modes; a fixed-seed, manifest-recorded Wasm-Smith JIT/interpreter differential corpus; verifier-negative and whole-object snapshots; and relocation, fixup, trap, safepoint, stack-map, unwind, and artifact-round-trip tests.
- 2026-07-16: AMD64 cutover additionally requires ASan/UBSan GC stress, and an AArch64 cutover may not introduce AMD64 sanitizer failures. Each target job records `uname -m` and rejects an unexpected architecture (`arm64`/`aarch64` for AArch64, `x86_64` for AMD64). Missing suites, timeouts, absent reports, and unparseable results are failures rather than evidence of success.
- 2026-07-16: Ordinary implementation commits run the common quality gates plus tests at every affected seam. Closing a migration ISS or performing a production cutover requires that issue's complete matrix, so reviewable intermediate commits remain practical without weakening milestone acceptance.
- 2026-07-16: Approved one versioned three-tier performance workload manifest shared by AArch64 and AMD64: a micro-codegen corpus covering scalar, control flow, direct/indirect/tail calls, stack arguments, multi-value returns, memory, SIMD, GC, exceptions, and references; a fixed subset of stable real algorithm modules with verified outputs; and large compile-stress modules covering large functions, many functions, complex CFG, register pressure, and dense metadata.
- 2026-07-16: Every manifest entry records a content checksum, entry point, expected output, internal iteration count, and intended metrics. The runner separates process startup, JIT compilation, and in-module execution. Target-specific exclusions require an exact host-capability reason and may not hide backend performance. The currently failing `core3`, `stream`, and `box_easy2` defaults must be repaired or explicitly replaced before baseline capture.
- 2026-07-16: Workload-manifest changes are standalone reviewed commits that rebuild both architecture-specific fixed-legacy baselines. A candidate cutover may not change the benchmark corpus or its expected outputs while using the resulting measurements for acceptance.
- 2026-07-16: Approved normalized structural comparison rather than byte, layout, or physical-register identity. At semantic-producer cutover, normalized function signatures, blocks and edges, block arguments, operations, effects, traps, calls, and safepoints must match exactly. At target cutover, instruction selection, layout, physical allocation, constant pools, and final offsets may differ, but every stage must pass its verifier.
- 2026-07-16: Relocations and fixups compare `(function, semantic site, kind, target, addend)` while ignoring final code offsets. Traps compare `(function, Wasm source offset, trap kind)` with no missing or additional sites. Safepoints and stack maps compare semantic site plus live-root identity and type; each candidate root must resolve to a valid register or stack slot. Calls compare callee kind, signature, ABI argument/result assignment, clobber contract, and tail-call kind. Frame and unwind comparison requires recoverability, callee-save correctness, stack alignment, and legal frame size but not identical frame size.
- 2026-07-16: Normalized disassembly is diagnostic and review evidence, not the sole hard oracle. If metadata cannot be aligned by a stable semantic-site identity, the implementation must introduce a stable ID before comparison; array order and machine-code offsets are not accepted substitutes.
