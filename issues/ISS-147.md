# ISS-147: Enforce MilkIR function ownership

## Metadata
- Type: bug
- Status: closed
- Priority: 0
- Labels: milkir, ir, ssa, verifier, builder, correctness, agent
- Assignee: codex
- Created: 2026-07-13
- Updated: 2026-07-13
- External ref: PR #421

## Description
MilkIR values and blocks carry only function-local numeric IDs. A `Value` or `Block` created by one function can therefore be passed to another function's builder, and the verifier may silently reinterpret a foreign value as a local definition when its ID and type collide. Switching a builder to a foreign block also lets one function append instructions directly into another function's block. This can silently miscompile valid-looking IR.

## Design
Give every function a private identity token and stamp all function-owned values, blocks, and instructions with that token. Preserve the existing printed and debug representation, remove the public raw `Value` constructor, reject foreign entities at builder and low-level mutation boundaries, and make the verifier independently check ownership so malformed white-box IR cannot pass by ID collision.

## Acceptance Criteria
- [x] A builder rejects a block created by another function before changing its current block.
- [x] Builder operations reject values created by another function, including same-ID and same-type collisions.
- [x] `Block::append_inst` rejects an instruction created by another function without mutating the block.
- [x] A rejected low-level mutation persists `ForeignInstruction` for `verify` or `finalize` instead of silently deleting the instruction.
- [x] `Block::append_inst` rejects instructions whose args, operands, or results contain foreign values, leaves the block unchanged, and persists `ForeignValue`.
- [x] The verifier rejects foreign values, blocks, and instructions independently of builder checks.
- [x] Existing MilkIR printing and value debug output remain stable.
- [x] MilkIR tests, full native tests, warning checks, and module-boundary audit pass.

## Notes
- 2026-07-13: Claimed from a minimal probe showing that two builders can exchange blocks and same-ID `i32` values while both resulting functions still verify.
- 2026-07-13: Reopened after review found that public `Block::append_inst` still inserted a foreign instruction and relied on a later verifier call to detect it.
- 2026-07-13: Reopened again after review found that the owner guard silently dropped a rejected side-effecting Call and allowed the destination function to verify successfully.
- 2026-07-13: Reopened after review found that the instruction-owner guard did not inspect values stored in the instruction's args, operands, or results.

## Close Notes
Closed again on 2026-07-13. `Block::append_inst` now validates the instruction owner and every value in its args, operands, and results before mutating the block. A foreign instruction still records `ForeignInstruction`; a function-owned instruction containing any foreign value leaves the block unchanged and records the first `ForeignValue`. Independent regressions cover foreign arguments, operands, and results. Verified with `moon check --target native --deny-warn`, MilkIR tests (120/120), `MACHV_REGALLOC_VALIDATION=1 moon test --target native` (1814/1814), and the module-boundary audit.
